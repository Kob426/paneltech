# Задание для Codex: прототип панели маркировки игр

Ты работаешь как разработчик. Реализуй работающий прототип по этому заданию, а не только план или макет. Сначала изучи текущий репозиторий и AGENTS.md. Если проект уже существует, используй его архитектуру и не перезаписывай чужие изменения. Если каталог пустой, создай самостоятельный проект. Не меняй Patchhound или другое приложение без явного указания пользователя.

## 1. Задача и контекст

Пользователь работает в команде из шести сотрудников поддержки более 50 компьютерных клубов. Обращения приходят в отдельные Telegram-чаты клубов. Сейчас сотрудник в MeshCentral выбирает клуб и ПК, открывает терминал, удаляет прежние QoS-правила игры и применяет новые через PowerShell.

Частые симптомы: игра не запускается или не авторизуется, не подключается к серверу, высокий пинг, не работает голосовой чат. Поддержка перебирает доступные варианты маркировки. Для одной игры на разных ПК одного клуба могут помогать разные варианты. Найденные решения сейчас не фиксируются.

Ценность продукта: массовое применение, быстрое переключение вариантов, сохранение успешных решений по связке клуб + ПК + игра. Это самостоятельный продукт пользователя; возможна будущая интеграция с сайтом начальника.

## 2. Границы первого релиза

Реализовать браузерную панель, сервер и Windows-агент с исходящим подключением к серверу. Интеграция с MeshCentral не требуется. Не разрабатывать FACEIT, управление UWF, перезагрузки, загрузку игр, Telegram-бота, оплату и автоматический подбор по сетевым тестам.

Не отключать защиту диска. Не закрывать и не перезапускать игры автоматически. После перезагрузки ПК маркировки применяются заново только по новой команде сотрудника. История сохраняется на сервере, но не запускает восстановление правил.

## 3. Предлагаемый стек

Если нет существующего стека: TypeScript, Vue 3 + Vite для панели, Node.js для API, SQLite для прототипа. Windows-агент — .NET Worker Service с установкой как Windows-служба и режимом запуска из консоли для разработки. Сервер допускает локальный запуск в Windows. Для демонстрации не требовать Docker, MikroTik или настоящий клуб.

Версии и совместимость уточни по официальной документации в среде разработки; зафиксируй зависимости. Не усложняй микросервисами. Раздели web, server, agent, shared contracts и документацию. При обоснованной необходимости можешь изменить стек, объяснив причину в README.

## 4. Основной экран

Русский интерфейс. Слева список и поиск клубов. В центре таблица ПК: флажок выбора, номер/имя, доступность, время последней связи, состояние последней операции. Справа или сверху панель действий: игра, доступные варианты DSCP, последний успешный вариант для этого ПК, кнопки применения и удаления.

Для группы ПК не показывай один общий успешный вариант, если история различается. Показывай количество выбранных ПК и состав массового задания перед запуском. Для массового применения — компактное подтверждение с клубом, количеством ПК, игрой и вариантом. Для одного ПК достаточно явной кнопки действия.

Результаты выводить по каждому ПК. Недоступность одного компьютера не должна останавливать остальные. История фильтруется по клубу, ПК, игре и периоду.

Устройство имеет стабильный идентификатор, а не только hostname. Переподключение агента не создаёт новый ПК. Назначение устройства клубу выполняется при регистрации администратором.

## 5. Игры и варианты маркировки

У клуба собственный список доступных вариантов. Значения 36, 39, 40 и 41 — локальные идентификаторы действующей схемы клуба, а не универсальное значение маршрута DSCP. Не предполагай, что 39 и 41 доступны везде. Названия настраиваются; 36/40 можно подписать по данным пользователя, но не объявлять маршрутизацию подтверждённой автоматически.

Каталог игр содержит название и редактируемый список exe. Разрешать только имена исполняемых файлов, без команд, аргументов и произвольного PowerShell. Валидировать данные и на сервере, и в агенте. Полный поиск exe в интернете и автоматическое определение установленной игры не входят в MVP.

Единственный предоставленный пользователем пример набора — Epic Games Launcher + Fortnite:
- EpicGamesLauncher.exe
- EpicWebHelper.exe
- FortniteClient-Win64-Shipping.exe
- FortniteClient-Win64-Shipping_EAC_EOS.exe
- FortniteClient-Win64-Shipping_BE.exe

Это стартовый редактируемый набор из практики пользователя, не подтверждённый аудитом актуальных файлов. PUBG добавить как пустую карточку с требованием заполнить exe либо как явно демонстрационный набор, не выдавая выдуманные имена за проверенные.

## 6. Выполнение на Windows

Агент выполняет только фиксированные операции inspect_rules, apply_marking, remove_marking и health. Не создавать интерфейс произвольного удалённого выполнения команд. Задания содержат типизированные параметры, а не текст скрипта от сервера.

Использовать NetQosPolicy и PolicyStore ActiveStore согласно примеру пользователя. Перед реализацией проверить поведение команд в официальной документации Microsoft. Пример назначения: New-NetQosPolicy с AppPathNameMatchCondition и DSCPAction; удаление — Remove-NetQosPolicy; проверка — Get-NetQosPolicy. Права и наличие команд проверяются заранее; при отсутствии возвращается понятная ошибка.

Каждое собственное правило получает префикс продукта и стабильный идентификатор игры/правила. Не удалять все QoS-политики системы и не удалять сторонние правила только по похожему имени. Пользовательские старые политики могут иметь имена без префикса. Обнаруживай потенциальные конфликты, показывай их и возвращай conflict; автоматическую миграцию чужих политик в MVP не делать.

Переключение варианта должно быть идемпотентным: повторное назначение не создаёт дубликатов. Менять только правила выбранной игры. Хранить предыдущий собственный набор для отката при частичном сбое; результат отката и остаточные изменения отражать явно. Не называть последовательность PowerShell-команд атомарной транзакцией.

Учитывай общие exe: EpicWebHelper может присутствовать у нескольких игр. Обнаруживай пересечения наборов и несовместимые активные назначения на одном ПК; возвращай понятный конфликт, не перетирай их молча.

После изменения считать фактические значения правил. Успех задания означает, что ожидаемый набор проверен, а не только получен exit code 0. Сообщение: "Правила применены. При необходимости перезапустите игру". Это не подтверждает маршрут через MikroTik, пинг или работу голосового чата.

## 7. Задания и связь

Достаточно исходящего HTTPS polling агента. Не требовать входящих портов на клубном ПК. Локальная разработка допускает HTTP только на loopback, для связи между компьютерами нужен TLS.

Состояния: queued, running, succeeded, failed, expired, unknown. Добавить ограниченные повторы связи, таймауты, heartbeat и срок действия задания. На один ПК одновременно выполняется одна изменяющая операция. На сервере сохраняются задания и их результаты, чтобы перезапуск API не терял историю.

Не оставлять команды для офлайн-ПК до неопределённого момента: по умолчанию пропускать недоступные ПК, показывать причину. Перед выполнением проверять срок и идентификатор загрузочной сессии. Задание из прошлой сессии не выполнять после перезагрузки. После новой загрузки — инспекция состояния, без автоматического восстановления маркировок.

Повторная доставка того же job_id не должна создавать повторную операцию. Если связь пропала после изменения правил, показывать unknown, затем сверять фактическое состояние. Не обещать exactly-once при сетевых сбоях. Для ActiveStore учитывать фактическое состояние, дату инспекции и смену загрузочной сессии; устаревшие сведения не показывать как текущие.

Агент сохраняет учётные данные и минимальную информацию о выполнении между перезапусками процесса. Учесть, что при UWF запись на защищённый диск может исчезнуть после перезагрузки: документировать требования к постоянному размещению идентификатора и токена. Не менять исключения UWF автоматически. После согласования пилота установка в образ/постоянное хранилище выполняется отдельно.

## 8. История и отметки результата

Сохранять автора, время, клуб, ПК, игру, ревизию набора exe, выбранный вариант, технический результат и ошибку. Отдельная отметка сотрудника: помогло / не помогло / не проверено. Причины: запуск или авторизация, серверное подключение, пинг, голосовой чат, другое. Комментарий необязательный.

Рекомендацию брать из последнего отмеченного успешного применения для конкретного ПК и игры, показывать дату и причину. Старые записи сохранять при изменении каталога. Вариант из истории, недоступный сейчас в клубе, не должен становиться доступным для запуска.

## 9. Доступ

Нужны вход сотрудника, безопасное хранение паролей и сессий, роли администратора и оператора. Администратор управляет пользователями, каталогом, клубами и регистрацией агентов; оператор запускает операции и отмечает результат. На MVP оба видят все клубы.

Регистрация агента через одноразовый ограниченный по сроку токен с привязкой к клубу. После неё — отдельный отзываемый токен устройства. Агент может получать только свои задания и отправлять только свои результаты. Не включать токены в логи, не хранить общий секрет всех ПК в установщике. Учётную запись Windows-службы и необходимые права документировать.

## 10. Домашний режим демонстрации

Один локальный запуск поднимает панель/API и симулятор нескольких ПК в двух вымышленных клубах. Симулятор не требует прав администратора, не меняет QoS, не управляет UWF, не перезагружает ПК и не регистрирует настоящую службу.

Сценарии: успех, офлайн, ошибка прав, частичный сбой и откат, потеря связи после выполнения, конфликт правил, перезапуск симулированного ПК. DEMO заметен в интерфейсе и у результатов. Тестовые данные отделены от реальных.

Реальный Windows-агент поставляется в том же проекте. Для домашней проверки предусмотреть dry-run с валидацией задания без изменений системы. Реальное выполнение QoS включается явно на агенте, а не одной кнопкой в демонстрационной панели. Не устанавливать службу и не менять сеть личного ПК пользователя автоматически.

## 11. Приёмка

Прототип готов, если:
1. Из чистого checkout по README запускается домашняя демонстрация одной документированной командой после установки зависимостей.
2. Можно выбрать несколько ПК, применить вариант и увидеть индивидуальные результаты.
3. Недоступный в клубе вариант отклоняется и интерфейсом, и API, и агентом.
4. Переключение не затрагивает другие игры и сторонние правила; конфликт общих exe показан явно.
5. Повторная доставка задания не создаёт дубликаты; просроченная задача не выполняется после перезагрузки.
6. После имитации перезагрузки временные правила исчезают, история остаётся, автоматического применения нет.
7. Отметка "помогло" сохраняется и видна другой учётной записи; после перезапуска сервера история остаётся.
8. Отказ, частичное выполнение и неизвестный результат не выглядят как успех.
9. Есть инструкция установки и удаления настоящего агента, отзыва доступа и ограниченного пилота на свободном ПК клуба.
10. Проверки симулятора и реального Windows-агента честно разделены. Без Windows/MikroTik отметить соответствующие проверки как не выполненные.

## 12. Порядок работы и сдача

Сначала создай короткий план, затем реализуй вертикальный сценарий: вход → регистрация симулированного ПК → задание → результат → история. Затем массовые задания, каталог, конфликты, обработку сбоев и настоящий агент.

Пиши содержательные тесты на изоляцию устройств, валидацию, повторы, истечение задач, конфликты правил и восстановление после сбоев. Не ограничивайся скриншотом интерфейса. Сборку агента проверить отдельно; отсутствие Windows не подменять заявлением об успешном системном тесте.

Подготовь README.md, ARCHITECTURE.md, TASKS.md и PROJECT-STATUS.md с фактическим состоянием. Для пилота включи замер времени: терминал Mesh против панели на одинаковом наборе ПК. Не придумывай экономию или окупаемость.

В конце сообщи: что работает, как запустить, какие проверки пройдены, что осталось непроверенным, какой следующий шаг нужен для пилота. Не публикуй сервис, не устанавливай ничего на клубные ПК и не подключай настоящие клубы в рамках этого задания. Заверши локальный прототип без запроса разрешения на каждое обычное изменение проекта.
