# Нагрузка с автоматическими копиями

Отдельный Linux-стенд использует только собственные временные синтетические БД. Продуктовые API/очередь/Operations/backup-task/restore/retention выполняются настоящим кодом; физические ПК, Windows QoS, внешняя сеть и TLS не используются. Старые LOAD/SOAK отчёты не перезаписываются.

Команда основного профиля:

```sh
npm run measure:operations-load -- --seconds 900 --heartbeat-rps 600 --jobs 100000
```

52 клуба, 3380 устройств: 60 DEMO выполняют задания, 3316 HTTP-клиентов циклически отправляют heartbeat, четыре устройства зарезервированы. Шесть сотрудников читают state/history суммарно 6 раз/с; каждые 5 секунд создаётся группа из четырёх DEMO-заданий. Генератор open-arrival, максимум 64 незавершённых запроса/48 потоков. Любая ошибка или пропущенная заявка означает непрохождение профиля. 600 heartbeat/с не означают все устройства раз в две секунды.

Operations сам запускает первую копию через 60 секунд и последующие через 5 минут после завершения предыдущей попытки. Используется штатный минимум интервала, keep=2 и бюджет 512 МиБ. Это настройки стенда, обычный запуск продукта по-прежнему использует 6 часов/7 копий/1 ГиБ. Новый пакет проходит отдельный restore-drill прежде retention; отслеживается продолжающийся транзакционный маркер записи. Требуется минимум три успешных цикла, две оставшиеся копии и отсутствие skipped-пакетов.

После нагрузки две оставшиеся копии независимо verify/restore: побайтовая сохранность завершённой истории/audit, отзыв сеансов/токенов, queued→expired без попытки, running→unknown, три тика без повторного исполнения. SHA закрытого исходника до/после восстановлений должен совпасть. Начальные 100k jobs дополнительно сравниваются по SHA за весь живой прогон, новые DEMO jobs должны завершиться по одному разу.

Короткая диагностика стенда:

```sh
npm run measure:operations-load -- --quick --seconds 120 --heartbeat-rps 300 --jobs 10000
```

Только quick-профиль сокращает начальную задержку до 5 секунд и интервал до 30 секунд в частном harness, без изменения продуктовых настроек. Quick не заменяет основной профиль.

Метрики: latency p50/p95/max по HTTP, пропуски и ошибки, RSS/heap/lag API, размер main/WAL, сроки copy+restore+retention, число и объём копий. Каждые 0,2 секунды стенд отдельно читает приватный monitoring endpoint; его нагрузка добавляется к шести пользовательским чтениям. Метрики main/WAL/RSS снимаются раз в 30 секунд, краткие пики могут не попасть в выборку.

Не совмещать замер со сборкой, браузерными сценариями или другими нагрузочными проверками. Каталог/порт внешнего сервера не принимаются; control endpoints существуют только в scripts/operations-load-worker.ts и не входят в продукт. POSIX select/process metrics не проверены на Windows. RSS дополнительных непосредственных дочерних процессов API измеряется отдельно через Linux /proc; в него могут входить и служебные процессы tsx. Это не суммарная память всех потомков/генератора. Фактические результаты и SHA приведены ниже.

## Учёт очереди генератора

Первый основной 900-секундный прогон сохранил историю и прошёл три цикла backup/restore/retention, но получил 26 пропусков heartbeat и один чтения при лимите 64 pending. HTTP-ошибок не было. Он не считается пройденным. В драйвере найдено, что завершённые futures освобождались только в начале внешнего цикла, а не перед отклонением из-за ёмкости. Исправлено освобождение готовых результатов перед проверкой лимита; сам лимит 64 не увеличен. Добавлены dropReasons/dropSamples, а также две отдельные проверки освобождения готовых и сохранения ограничения активных запросов (`python3 tests/operations_load_generator.py`). Первый результат сохраняется с исходными SHA, итог повторного прогона учитывается отдельно.
