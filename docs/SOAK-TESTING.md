# Длительная синтетическая нагрузка и online backup

Стенд предназначен для Linux Codex/локального Linux с Node.js 24 и Python 3 standard library. Это отдельная проверка одного процесса API/SQLite на loopback, без настоящих клубных ПК, Windows, QoS, MikroTik, TLS и внешней сети. Производственная ёмкость и круглосуточная устойчивость этим не подтверждаются.

## Запуск

```sh
npm ci
npm run measure:soak
```

По умолчанию: 600 секунд, 100 000 завершённых заданий, 300 heartbeat/с. Для быстрой проверки самого стенда:

```sh
npm run measure:soak -- --seconds 30 --jobs 10000 --heartbeat-rps 100
```

Допустимы 30–3600 секунд, 10k/100k истории и 1–2000 heartbeat/с. Значение частоты задаёт предложенную нагрузку, а не обещает её успешную обработку. Стенд не принимает путь к пользовательской БД или внешний адрес, игнорирует DB_PATH и создаёт собственный tempfile-каталог с обязательным маркером. Временные базы, копии и процессы удаляются после проверки. JSONL в stdout содержит промежуточные замеры и итоговый result; сохраните вывод в отдельный файл, если нужны исходные метрики. Ошибки/тайм-аут/пропущенные отправки дают ненулевой exit code.

Не запускать одновременно с другими сборками, браузерными тестами или CPU-нагрузкой: иначе результаты нельзя сравнивать. Для обычного запуска панели Python не нужен. Здесь используется POSIX select для ожидания процесса; стенд на Windows не проверен.

## Профиль

- 52 вымышленных клуба по 65 устройств, всего 3380. История и аудит генерируются тем же seed, что в measure:load: 100k завершённых jobs, 20k audit и 52 старых unknown.
- 60 устройств первого клуба выполняют серверную DEMO-симуляцию. Через настоящий API каждые 5 секунд создаётся группа из четырёх apply_marking с чередованием 36/40; обычный Core.tick исполняется раз в секунду. Windows-исполнитель не используется.
- 3316 других устройств получают синтетические HTTP poll по индивидуальным токенам, inspectionVerified=false, без новых команд. Ещё четыре устройства зарезервированы; два содержат canary queued/running с долгим TTL для проверки восстановления. Старые unknown остаются заблокированными.
- Шесть тестовых сотрудников отправляют суммарно 6 чтений/с: state выбранного клуба и серверные страницы истории, с обходом клубов. Проверяются 65 устройств в scoped state, отсутствие tokenHash и максимум 25 строк истории.
- Частота heartbeat по умолчанию 300/с: один обход 3316 устройств примерно за 11 секунд. Это значительно реже polling всех устройств каждые 2 секунды; такая ёмкость не заявляется.

Python задаёт время новых запросов независимо от завершения предыдущих (open arrival). До 48 потоков, не больше 64 незавершённых запросов. При заполнении лимита или опоздании планировщика больше секунды отправка учитывается как dropped и весь прогон считается неуспешным. Автоматических повторов POST нет. Client latency измеряется от начала HTTP-запроса; ожидание до его начала отдельно отражено в schedulerLag. Дополнительные login/control/metrics запросы не включены в счётчики нагрузки.

## Копирование и восстановление

Две штатные CLI-команды db:backup запускаются отдельными процессами на 20% и 65% окна, пока API продолжает обслуживать нагрузку и выполнять задания. Запись двух marker records одним transaction каждую секунду позволяет проверить согласованность снимка и продвижение записей между началом/концом backup. Стандартные WAL, autocheckpoint и настройки сохранности не отключаются. wall-limit процесса backup — 90 секунд; внутренний timeout самого SQLite-copy — штатные 30 секунд. Процесс backup может также тратить время на integrity/schema/hash проверки до/после копирования.

Первый основной прогон выявил starvation backup: при 300 heartbeat/с внешний writer постоянно перезапускал copy, и штатный timeout 30 секунд сработал примерно на 150-й секунде теста. Этот запуск не считается успешным; его неудача сохраняется в итоговом отчёте.

Исправление в createBackup: BEGIN до проверки исходника закрепляет один WAL read snapshot; COMMIT сразу после SQLite-copy освобождает reader до destination validation/hash/fsync. API-writer продолжает работать, а изменения после начала снимка попадут в следующую копию. При исключении соединение закрывается, reader освобождается и staging удаляется. Мелкие порции, timeout, SHA/манифест и проверки целостности сохранены. Цена удержания snapshot — временный рост WAL, который измеряется в прогоне; копии не стоит выполнять бесконтрольно параллельно.

Поведение restart описано в официальной [Node.js SQLite backup API](https://nodejs.org/docs/latest-v24.x/api/sqlite.html#sqlitebackupsourcedb-path-options), влияние долгого читателя на WAL — в [SQLite WAL/checkpoint](https://sqlite.org/wal.html#checkpointing). Регрессии проверяют commits на каждом copy-step, монотонное уменьшение remainingPages, исходное поколение в копии и освобождение reader/checkpoint как после успеха, так и после намеренной ошибки.

После завершения нагрузки API закрывает БД. Оба backup-пакета проходят штатные verifyBackup/restoreBackup только в **новые** файлы. Проверяются:

- Совпадение маркеров одной транзакции, SHA/манифест, integrity/schema.
- Побайтовая сохранность каждой завершённой операции и raw audit records относительно соответствующей копии.
- Отзыв сеансов и доверия устройств, отсутствие токенов, очистка собственных DEMO-правил.
- Canary queued становится expired без исполнения (attempts=0), running — unknown (attempts=1); прочие unknown остаются неопределёнными.
- Три Core.tick восстановленной БД не создают/не исполняют задания и не меняют историю.
- SHA файла закрытого исходника до/после двух восстановлений совпадает.

Старые исходные jobs дополнительно сравниваются по SHA за весь живой прогон. Для новых команд проверяются точное число записей, успешный DEMO-результат и attempts=1; любой пропуск, повтор, timer exception или halted Store завершает проверку ошибкой.

## Метрики и границы

Каждые 30 секунд: текущий/максимальный RSS Node, heap, p95/max event-loop lag, размеры main/WAL, progress marker, счётчики ошибок/пропусков. Итог: предложенные/выполненные запросы и p50/p95/max отдельно для heartbeat, чтений и создания групп, scheduler lag, максимальный ответ, два backup/restore протокола, хеши выбранных источников.

RSS относится только к API-процессу; процессы клиента/backup/restore в него не входят. Размер WAL — выборка раз в 30 секунд, кратковременный пик между выборками может быть выше. Backup-пакеты учитываются отдельно. Исходные 10 минут не доказывают отсутствие утечки за сутки, поведение при неограниченной истории, disk-full/power-loss, Windows/NTFS/SMB, внешний TLS/сеть, работу нескольких API и полную нагрузку всех агентов с интервалом 2 секунды.

## Результат прогона

Фактический полный прогон 24.10.2026, Node 24.19.0 / SQLite 3.53.3, один API-процесс: **600 секунд при 300 heartbeat/с**, 100k исходной завершённой истории, 52 клуба/3380 устройств. Все предложенные запросы выполнены, **ошибок и dropped нет**. Название CPU хоста в JSON не означает выделенное число ядер.

| Запросы | Выполнено | p50, мс | p95, мс | max, мс |
| --- | ---: | ---: | ---: | ---: |
| Heartbeat | 180 000 | 1,08 | 15,39 | 61,51 |
| Чтения панели/истории | 3600 | 22,51 | 30,56 | 61,01 |
| Создание групп | 120 | 16,34 | 32,81 | 44,00 |

480 новых DEMO-операций завершились успешно с attempts=1; старая история не изменилась. Максимальный ответ 187 652 байта. Опоздание планировщика p95 2,10 мс, max 42,38 мс; это измеряется отдельно от HTTP latency. Наибольшее наблюдавшееся число незавершённых запросов — 20 из лимита 64.

Максимальный RSS API **316,15 MiB**, в конце 314,75 MiB. Последние пять выборок RSS примерно 314,84–315,02 MiB; это наблюдение за 10 минутами, не доказательство отсутствия утечки за сутки. p95 event-loop lag 18,87 мс, max 61,60 мс. Main в выборках 96 731 136→97 374 208 байт; максимальный *наблюдённый* выделенный WAL 19 186 872 байта (18,30 MiB). Между выборками возможны иные пики. После checkpoint выделенный WAL может переиспользоваться без сокращения физической длины.

Оба штатных db:backup прошли при продолжающихся записях:

| Копия | Интервал от старта API, с | Marker до→после | Размер standalone SQLite |
| --- | --- | --- | ---: |
| 1 | 120,25–132,11 | 121→133 | 96 878 592 байта |
| 2 | 390,25–401,81 | 391→402 | 97 161 216 байт |

Это полное время CLI с проверками, не только SQLite-copy. Обе копии отражают согласованный marker начала snapshot (121 и 391), а не более поздние commit. Каждая содержит 5 queued-команд (canary + 4 ещё ожидавшие DEMO-операции); при restore они стали expired без исполнения. Running canary и 52 старых unknown сохранились как 53 unknown. Завершённая история и аудит сохранены; сеансы/доверие отозваны, собственные DEMO-правила очищены. Три tick каждой восстановленной базы ничего не переисполнили. SHA закрытого исходника до/после восстановления совпал.

Сырые выборки, хеши исходников, неудачный первый прогон и успешный повтор — [SOAK-RESULTS.json](SOAK-RESULTS.json). Короткий smoke 30 секунд / 10k / 100 heartbeat/с тоже прошёл и сохранён отдельно как проверка стенда. Затем, **после завершения** замеров, прошли typecheck/build, 140/140 Node-тестов, шесть Chromium-сценариев и database CLI/API smoke. Нагрузка на всех агентов раз в 2 секунды, многочасовая работа, физические отказы, сеть/TLS и Windows остаются непроверенными.

После блока доступа агентов 4.37 сервер/core изменены. Зафиксированные выше цифры относятся к прежним SHA источников в JSON-отчёте; нагрузка в 4.37 не перемерялась. Старые метрики/хеши сохранены как историческое доказательство, а не замена проверки новой версии.

Блок 4.38 добавил расписание/отдельный worker и restore-drill каждой копии. Этот новый профиль под прежней массовой нагрузкой ещё не перемерялся; исторические JSON/SHA не заменяются текущими тестами таймера и восстановления.
