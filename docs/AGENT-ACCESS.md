# Доступ агента: регистрация, смена секрета и восстановление

Реализовано и проверено в Linux на временных БД и настоящем .NET-процессе **только в dry-run**. Настоящий Windows, служба SCM, ACL/NTFS, UWF, QoS и реальные клубные ПК не проверялись и не подключались. В обычном DEMO регистрация/смена/восстановление настоящих агентов отключены. Примеры ниже — инструкция для отдельно согласованной лаборатории, не разрешение подключать рабочий клуб.

## Первая регистрация и потерянный ответ

Обновлённый агент сначала сохраняет receipt-файл и стабильный deviceId, затем генерирует CSPRNG-секрет и записывает его вместе с registrationPending в identity.json **до** POST /api/agent/register. Сервер хранит только SHA-256 секрета. Клуб задаётся одноразовым enrollment администратора, а не hostname/параметром агента.

Если ответ потерян после commit, при следующем запуске GET /api/agent/access с уже записанным кандидатом подтверждает исходный ID. Повторная регистрация/новый ID не нужны; подтверждение работает и после истечения enrollment. Если commit не было, тот же кандидат повторяет регистрацию только с ещё действующим исходным enrollment-файлом. Сервер допускает точный повтор deviceId+candidate+enrollment, без второй записи и второго audit event. Другой ID/кандидат, отозванный доступ и повтор после смены секрета не принимаются.

Старый формат регистрации без client candidate остаётся совместим с прежними агентами, но не получает новый механизм восстановления потерянного ответа. Перед использованием смены токена обновите агент. Старый агент игнорирует rotateToken и не получит новые команды, пока запрос не будет обработан обновлённым агентом.

## Смена токена

Администратор выбирает **Управление → Доступ агентов → Сменить токен** для активного настоящего устройства. Это запрос на смену при следующем polling, не мгновенный отзыв. Для немедленной блокировки нужна отдельная кнопка «Отозвать».

Пока смена запрошена, poll возвращает job=null и rotateToken=true; уже начатый результат можно передать. Агент записывает pendingToken до обращения к серверу. Затем проверяет, не принят ли этот кандидат уже, и при необходимости отправляет POST /api/agent/access/rotate с текущим секретом и expectedAccessVersion. Сервер одной транзакцией меняет hash/version, снимает запрос и пишет безопасный audit event. Старый токен сразу перестаёт работать, grace-секрета на сервере нет.

Потеря ответа или сбой локальной записи после commit не стирают pendingToken с диска: после restart агент подтверждает его через /access и завершает локальное сохранение. Receipt/outbox, stable ID и boot не меняются; ожидающие задания остаются исходными. При неясности новый кандидат разрешается **до** отправки outbox/нового poll. Сбой durable записи останавливает процесс. Значения токенов не печатаются.

Это ручная смена по запросу администратора, без автоматического календарного расписания. Секрет генерирует сам агент, панель его не получает и не показывает.

## Потеря identity, receipts или ownership

Не удаляйте state и не используйте новый обычный enrollment для уже известного ПК: при полной утрате хранилища программа не может доказать, что это прежнее оборудование. Восстановление выполняет администратор по **существующей** записи/UUID. Автосопоставления по имени и аппаратной аттестации нет.

1. В панели выбрать нужный стабильный ID и нажать «Восстановить доступ». Само открытие подтверждения ничего не отзывает.
2. Подтвердить «Отозвать доступ и выдать файл». Старый секрет немедленно отзывается, queued становятся expired, running/unknown сохраняются как unknown; новые команды недоступны. Выдаётся JSON-файл на 10 минут, привязанный к устройству/клубу/адресу сервера. Повторная выдача или «Отозвать» аннулируют предыдущий код. Пароль сотрудника не заменяет этот код.
3. Скачать файл через панель и передать уполномоченному локальному администратору правильного ПК. Это секрет доступа: не публиковать, не класть в репозиторий/общую папку. Панель очищает его при смене клуба/вкладки/аккаунта; после потери ответа/файла код нельзя прочитать из БД заново — обновите список и явно выдайте новый.
4. Остановить старый процесс/службу и проверить правильный config/stateDirectory. Затем **локально**, для лаборатории:

```sh
dotnet PanelTech.Agent.dll --config agent.json --recover-file paneltech-recovery-DEVICE-ID.json --confirm-state-reset
```

Команда не подключается к API, не вызывает PowerShell, не изменяет Windows-правила и не устанавливает службу. Без --confirm-state-reset, при работающем агенте (lock), неверном/истёкшем файле или отличающемся origin подготовка не выполняется. Config.ServerUrl должен соответствовать serverOrigin из файла; нельзя переносить действующую identity на другой сервер простой правкой config.

Подготовка сохраняет recovery-plan.json с кандидатом и этапом, перемещает identity/receipts/ownership/rollback и их .tmp в отдельный quarantine-UUID, создаёт новый пустой receipt-файл и identity с **тем же ID**. Прежние файлы не переписываются; новый ownership не создаётся. Повтор с тем же файлом сохраняет кандидат; прерванный этап archive/initialize можно продолжить той же командой. Наличие незавершённого plan запрещает обычный запуск. Повреждённый plan/незавершённый первый .tmp требует локального разбора, автоматическое угадывание состояния не выполняется. Flush/atomic rename не доказывают устойчивость к физической потере питания.

5. Запустить агент обычной командой. Для проверки доступа в dry-run:

```sh
dotnet PanelTech.Agent.dll --config agent.json
```

Он подтверждает уже принятый кандидат либо обменивает recovery grant на тот же сохранённый кандидат. Потерянный ответ восстанавливается через /access без повторной выдачи; ID/клуб/имя на сервере сохраняются. Изменение секрета и audit записываются вместе. После подтверждения recoveryToken удаляется из identity, но секретные карантин/файл надо хранить и удалять по локальной согласованной политике. Никакого --enable-qos эта инструкция не включает.

## Старые задания и правила

Восстановление меняет серверную commandEpoch. Старые queued не выдаются, старый outbox с новым токеном не принимается даже при совпадающих ID/boot. Новый агент не читает карантин как исполняемый журнал. Старая подтверждённая история сохраняется.

Dry-run не подтверждает инспекцию: старые unknown остаются заблокированными. После настоящей свежей инспекции агентом старый unknown с иной epoch завершается как **неподтверждённый failed**, а не как успех. Даже отсутствие owned-политик после потери manifest не выдаётся за успешное выполнение прежнего remove. Новые действия сотрудник создаёт явно.

При потерянном/карантинированном ownership существующие правила считаются чужими. Префикс PanelTech не даёт права присвоить/удалить их. Применение поверх конфликта остановится; нужна локальная ручная инспекция уполномоченным администратором. Автоматического восстановления правил из истории нет. Отзыв/восстановление не отменяет мгновенно уже начатое Windows-действие и не удаляет действующие политики.

## API и границы

- GET /api/agent/access: индивидуальный Bearer, ID/club/version, без выдачи секрета.
- POST /api/agent/access/rotate: Bearer + newToken/expectedAccessVersion; current hash меняется атомарно, коллизии с другим устройством запрещены.
- POST /api/admin/devices/:id/rotate и /recovery: admin + session/CSRF + expectedAccessVersion; 409 при устаревшем доступе.
- POST /api/agent/recover: одноразовый device-bound recoveryToken + deviceId/deviceToken/bootId, без права выбрать другой клуб.
- POST /api/admin/devices/:id/revoke также отменяет pending recovery; used/expired коды не возвращают другой действующий секрет.

Все агентские endpoints сохраняют запрет обычного HTTP вне loopback, включая forwarded HTTP. В БД — hashes, в журнале — ID/автор/время/номер версии/срок, без credentials. `/state` и audit не раскрывают секреты/hashes. Нормальный backup/restore удаляет enrollment/session и отзывает доверие устройств; старый файл восстановления не превращается в новый доступ после restore.

Физическая идентичность ПК, доверенный TLS/proxy/host, Windows ACL/SCM/NTFS/UWF, аппаратные отказы, защита карантина/off-site остаются задачами лаборатории/эксплуатации. В 4.40 код переведён на .NET 10 LTS; Linux-проверки новой платформы учитываются отдельно от исторического отчёта 4.37. Несколько API-процессов и полноценный пентест не проверены.
