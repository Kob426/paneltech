# Изменение каталога и вариантов при unknown

Выполнена задача 4.13. Проверки относятся к Linux DEMO и протоколу API с подготовленными HTTP-фактами. Это не инспекция Windows QoS и не подтверждение реального DSCP/маршрута.

## Правило поведения

Задание хранит исходные gameId, имя игры, revision, exe, числовой вариант и его имя, имя клуба, allowedVariants и bootId. Изменение карточки или вариантов клуба не переписывает этот снимок.

- **До выдачи queued:** apply проверяется по текущим вариантам клуба и исходным allowedVariants. Удалённый вариант даёт failed/variant, job агенту не выдаётся, attempts остаётся 0. Это одинаково для DEMO и агентского poll. Дополнительная проверка перед действием в DEMO и локальная проверка агента сохраняются.
- **После выдачи / при unknown:** новое изменение на этом ПК блокируется до результата или сверки. Сама правка каталога не является основанием повторно исполнить команду.
- **При сверке:** фактический набор сравнивается с исходным снимком задания и его bootId. Совпавший старый набор может дать succeeded, даже если его вариант уже удалён. Это означает совпадение наблюдаемого набора с историческим заданием во время сверки; оно не разрешает снова применять удалённый вариант и не доказывает, каким процессом правила были созданы.
- Совпадение только с новой карточкой, неполный/лишний набор, неправильный DSCP, имя/ownership либо другая загрузочная сессия дают failed. Неподтверждённая инспекция не снимает unknown.
- Сверка ничего не меняет в правилах. Она обновляет наблюдаемые факты и результат. Для нового применения нужна новая явная команда с текущей карточкой и разрешённым вариантом. Удаление варианта не удаляет и не откатывает уже существующие правила.
- Поздний ответ уже завершённого задания не переписывает результат сверки или актуальное состояние устройства.

Сообщения DEMO/API теперь называют ревизию снимка и отсутствие повторного применения. Отметка «помогло» остаётся исторической; если текущая ревизия другая, таблица ПК показывает «ревизия изменилась…; проверьте exe». Удалённый вариант дополнительно подписан «сейчас недоступен». Никакого автоматического выбора из такой рекомендации нет.

## Исправленный дефект

Ранее Core.poll переводил queued в running до проверки текущей доступности варианта. DEMO проверял вариант перед мутацией, а .NET — по allowedVariants из ответа; сервер всё же мог выдать агенту уже запрещённое задание. Добавлена общая проверка **до выдачи**. До исправления два regression-теста воспроизводили выдачу такого задания; после исправления оба проходят.

## Проверки

`tests/catalog-reconciliation.test.ts` содержит 13 новых тестовых методов. Проверены:

- DEMO unknown с совпавшим исходным набором и с набором из новой карточки, сохранность снимка/фактов/attempts, запрет нового изменения и разрешение новой явной команды после сверки;
- запрет выдачи удалённого queued-варианта через Core и HTTP agent poll, неизменность правил и attempts=0;
- queued с новой текущей ревизией при всё ещё разрешённом варианте: исполняется исходный снимок;
- remove/unknown после правки и удаления текущей карточки: проверяется отсутствие собственных правил исходной игры, сохраняются сторонние правила и другая игра;
- зарегистрированный HTTP fixture с одноразовым enrollment и индивидуальным Bearer: новая карточка/варианты, matching/mismatch, dry/unverified inspection, новый boot, поздний unknown после terminal, отсутствие карточки и переименование разрешённого варианта;
- отсутствие/лишнее правило, неверный DSCP, имя и ownership: только failed, без повторной мутации.

В HTTP-тестах нет Windows-процесса: тест сам сообщает набор правил, моделируя ответ зарегистрированного агента. Отсутствующая карточка подготовлена прямо в тестовом Store; production API удаления карточек не добавлялся.

Браузерный smoke дополнен реальными API-операциями над отдельной DEMO SQLite: apply/lost → unknown → изменение exe/revision и удаление варианта → busy для новой операции → отдельная сверка старого набора. Проверены сохранность правил, снимка и attempts=1, предупреждения о ревизии/недоступном варианте, явный выбор оставшегося варианта. Итоговые desktop/mobile PNG осмотрены; pageerror и overflow на проверенных экранах отсутствуют.

Итог этого блока: **61/61 Node-тест**, typecheck, build, оба Chromium-сценария и `python3 tests/agent_smoke.py` прошли. Содержимое C# и JSON-схема протокола не менялись, поэтому .NET не пересобирался; выполнен существующий интеграционный Linux dry-run с настоящим API. Новые тесты автоматически входят в npm test и CI; удалённый Actions-статус не подтверждён.

Не проверены Windows NetQos/SCM/UWF, потеря питания и изменения GPO. Авторизация варианта перед выдачей не даёт мгновенной отмены уже выданного/начавшегося действия; сверка всё равно требует свежих наблюдаемых фактов. Остальные дисковые/протокольные отказы и backup/migrations остаются следующими задачами этапа 4.
