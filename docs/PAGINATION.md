# Задания и история: фильтры и страницы

В панели обе вкладки используют серверные фильтры: текущий клуб, стабильный ID ПК, игра, сотрудник, технический статус и период создания операции. В задачах также доступны batch и ввод полного ID задания. Список выбора содержит 25 последних групп; старую можно открыть из истории или по полному ID. Сотрудники берутся из исторических авторов клуба, включая отключённые/удалённые аккаунты. Это автор операции, а не автор последней отметки «помогло».

По умолчанию 25 операций на странице, варианты 10/25/50/100. Фильтр или размер страницы сбрасывает страницу на первую. Фильтры сохраняются между страницами и вкладками в текущем входе; переключение клуба/пользователя сбрасывает контекст. После перезагрузки браузера фильтры не восстанавливаются из localStorage/URL. В истории даты идут от новых к старым; в задачах незавершённые идут первыми. Период относится к `created`, включительно с обеих сторон. Ввод времени — в локальном часовом поясе браузера; сервер получает Unix milliseconds. Начало после конца и некорректные даты отклоняются.

«Открыть задание» и переход из истории сбрасывают мешающие фильтры и находят страницу конкретной операции; не нужно вручную листать большую группу. Счётчики и состав группы вычисляются по всей группе текущего клуба, независимо от страницы/автора/статуса/периода. На странице может быть один результат, а в сводке — весь mixed-result batch. Ошибка, unknown и ожидание остаются отдельными числами.

## Обновление выборки

Первый запрос фиксирует верхнюю границу вставленных записей (`snapshot` — SQLite rowid). Следующие страницы исключают добавленные после неё операции, в том числе с более ранним временем создания. «Обновить выборку» начинает новую выборку с первой страницы. Это предотвращает сдвиг страниц новыми вставками.

Статусы/отметки существующих операций продолжают обновляться. Это **не неизменяемый снимок всей базы**: при смене статуса фильтр, счётчики и порядок страниц могут измениться. Страницы за пределами нового количества автоматически ограничиваются последней. Незавершённые операции всегда доступны в рабочем экране/карточке; переход к ним создаёт свежую выборку. POST автоматически не повторяется.

Запоздавшие ответы прежнего фильтра/страницы/вкладки отбрасываются. Загрузка не выглядит готовой пустой историей. Ошибка показана отдельно, чтение возобновляется после восстановления связи; есть ручная повторная загрузка. Обновление статусов не перехватывает фокус у фильтра.

## API

`GET /api/history` теперь возвращает объект страницы **вместо прежнего массива**. Внутренние клиенты и проверка Linux-агента обновлены. Cookie-сессия обязательна; оператору административный доступ не нужен.

Параметры: `clubId`, `deviceId`, `gameId`, `batchId`, `author`, `state`, `from`, `to`, `page`, `pageSize`, `snapshot`, `focusId`, `order`. Все строковые идентификаторы сравниваются точно; author чувствителен к регистру. `state`: queued/running/succeeded/failed/expired/unknown либо active (queued/running/unknown). `order`: recent (по умолчанию) или active. Неизвестные параметры, дробные/отрицательные страницы, некорректные периоды и pageSize >100 возвращают 400. SQL использует связанные параметры.

Ответ: `items`, `total`, `page`, `pageSize`, `pages`, `snapshot`, `authors`, `batches`, `batch`. `pages` минимум 1, даже для пустого результата. `focusId` находит страницу целевой операции только внутри текущих фильтров/клуба/выборки. `batch` содержит first, полные counts и members; null, если группа в клубе не найдена.

`GET /api/state?clubId=…&gameId=…` отдаёт последние 60 операций клуба и все его queued/running/unknown, плюс последние операция/успешное применение/«помогло» для каждого ПК выбранной игры. Старые рекомендации и unknown не теряются после ограничения ленты. Без контекста возвращаются 60 последних глобально и все незавершённые. Это ограничение завершённой истории, не жёсткий лимит всего state: устройства/игры/клубы и незавершённые записи могут расти.

Четыре идемпотентных expression index SQLite добавляются при открытии базы (клуб/дата, ПК/игра/дата, статус, batch/клуб). Формат records и сохранённые записи не меняются. Версионированные миграции и online-backup реализованы следующим блоком — [BACKUP-RESTORE.md](BACKUP-RESTORE.md). Очередь/expire/сериализация всё ещё рассчитаны на один процесс; часть обработки сканирует историю, нагрузка 50+ клубов не измерена.

## Проверки

`npm test`: 80 тестов, включая девять новых по страницам/фильтрам/границам/старым фактам/полному batch/индексам/сессиям. `npm run test:browser`: пять Chromium-сценариев, новый `tests/browser_pages.py` использует отдельную временную SQLite и loopback 3106. Проверяет 201→202 операций, синтетическую группу из 120 записей, старую операцию на пятой странице, потерю порядка ответов, фильтры, новые вставки, контраст/overflow desktop 1512 и mobile 390. Это тестовые записи симулятора, не результаты настоящих ПК и не нагрузочный benchmark. Windows QoS здесь не проверяется.

## Индексы и устройства выбранного клуба (v5)

Горячие Core/agent операции используют активную очередь вместо всей истории; workspace окна последних успехов/«помогло» используют индекс выбранного клуба. Scoped GET /api/state возвращает devices только этого клуба, а все clubs получают deviceCount/onlineCount. Sidebar обновлён, запрос без clubId по-прежнему возвращает все устройства. Snapshot/filters/page и история/feedback контракты сохранены. Нагрузка 52 клубов/100k jobs и ограничения — [LOAD-TESTING.md](LOAD-TESTING.md).
