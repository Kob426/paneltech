# Экономное хранение данных

PanelTech использует встроенную **SQLite**. Отдельный сервер БД, Docker и платная облачная БД для локального запуска не нужны. Данные находятся на компьютере, где запущен API: сейчас это облачная среда Codex, при запуске у пользователя — его ПК. При будущем отдельном сервере база будет на этом сервере, не на каждом клубном ПК.

Личный режим хранит данные в `.data/local.sqlite`, открытый DEMO — в `.data/demo.sqlite`; изменить путь можно через `DB_PATH`. Пока API работает, рядом могут находиться служебные `-wal` и `-shm`. Резервировать работающую базу нужно через `db:backup`, а не копированием одного файла. В БД сохраняются аккаунты/хеши паролей, клубы, каталог, ПК, задания, результаты, история и отметки «помогло». Бинарники игр, обновления FACEIT, установщики и видеозаписи сюда не загружаются.

## За счёт чего экономится место

В схеме **v3** повторяющиеся списки exe и правил не копируются целиком в каждую запись истории. Крупные массивы `job.exes`, `job.rules`, `device.rules` канонизируются и сохраняются один раз в таблице `snapshots` по SHA-256 содержимого. Если DEFLATE уменьшает размер, сохраняется сжатый BLOB, иначе исходный. Массивы меньше 128 байт остаются в JSON. Отдельные результаты, статусы, авторы и комментарии сохраняются в записях заданий с прежними индексами для поиска.

Смена каталога/варианта создаёт новый снимок; прежний остаётся доступен истории. Снимки неизменяемые, чтение возвращает независимые объекты. API и агент получают полные массивы, внутренние ссылки в клиент не выходят. Проверка базы и backup проверяют ссылки, размер распакованных данных и SHA-256. История и пользовательские отметки ради экономии **не удаляются**. Файлы БД/копий не зашифрованы: сжатие не заменяет защиту доступа.

## Фактический замер

23.10.2026, Linux, Node 24.19.0 / SQLite 3.53.3. Две синтетические истории по 20 000 операций, 65 логических ПК, шесть сотрудников, пять exe, восемь ревизий и два варианта. В первом профиле все задания успешны и содержат правила, во втором смешаны успешные/ошибочные/истёкшие/неизвестные результаты. Обе сравниваемые базы закрыты и уплотнены; учитывается весь SQLite-файл с индексами, не только сжатый BLOB.

| Профиль | Прежняя v2, байт | Новая v3, байт | Уменьшение |
| --- | ---: | ---: | ---: |
| Применения с полным набором правил | 44 670 976 | 20 054 016 | 55,11% |
| Смешанные исходы | 30 945 280 | 20 013 056 | 35,33% |

Все поля заданий и их rowid сравнены до/после преобразования: логическое содержимое истории совпало. В этих профилях получается около 1 КБ на операцию с долей индексов/служебных данных. **Это не гарантированный размер реальной истории:** длинные комментарии, новые exe и разнообразные правила меняют результат. Это замер места на диске, не тест нагрузки 50+ клубов и не проверка Windows-маркировки.

Повторить на временных синтетических БД, без обращения к вашей `.data`:

```sh
npm run measure:storage
```

## Посмотреть размер своей базы

```sh
npm run db:stats -- --db .data/local.sqlite
```

Команда читает существующую базу и выводит JSON: `databaseBytes`, `walBytes`, `shmBytes`, `totalBytes`, `freePages`, `reusableBytes`, число/суммарный исходный и сохранённый размер уникальных снимков. `reusableBytes` — свободные страницы внутри файла, которые SQLite может использовать повторно; это не отдельное место на диске. `snapshots.rawBytes` относится только к уникальным массивам, не ко всем заданиям. На работающем API размеры могут изменяться во время чтения.

## Старые базы и уплотнение

Новая база создаётся в текущей v5 со сжатием снимков v3. Поддерживаются старые схемы v0–v4; перед обновлением остановите API и используйте миграцию с обязательной проверенной копией:

```sh
npm run db:migrate -- --db .data/local.sqlite
```

Миграция сохраняет ID, rowid и логическое содержимое, но освобождённые страницы могут остаться внутри SQLite-файла. Для физического уменьшения есть отдельная команда:

```sh
npm run db:compact -- --db .data/local.sqlite --to .data/local-compact.sqlite --out .data/backups
npm run db:check -- --db .data/local-compact.sqlite
```

**Это создание новой восстановленной копии, а не замена активной БД.** Сначала создаётся проверенный backup, затем в отдельном файле выполняются миграция, удаление только неиспользуемых общих снимков и VACUUM с сохранением rowid истории. Источник остаётся прежним. Существующий путь назначения или его WAL/SHM/journal запрещены. Команда сообщает размеры до/после и путь backup. Временно нужно место под оригинал, backup и новый файл со staging; точную потребность заранее не гарантируем.

К новой базе применяются **все правила восстановления**: старые сеансы/enrollment удаляются, queued → expired, running → unknown, реальные токены отзываются; у DEMO новый boot и очищены текущие собственные правила симулятора. Завершённая история/отметки остаются. Это предотвращает исполнение старых команд после переключения. Изменения исходной БД после момента backup в новый файл не попадают. Для перехода без потери новых записей сначала остановите API.

Переключать `DB_PATH` нужно вручную после проверки, как в [BACKUP-RESTORE.md](BACKUP-RESTORE.md#проверить-личную-восстановленную-панель), указав `.data/local-compact.sqlite`. Войдите заново и проверьте данные; оригинал/backup сохраняйте до завершения проверки. Linux-процедура проверена; Windows/NTFS/SMB и восстановление реальных устройств ещё не проверялись.

Автоматическое расписание копий, ограничение их числа, шифрование, перенос на другой носитель и мониторинг места пока не реализованы. История автоматически не обрезается. Часть логики очереди всё ещё сканирует историю; экономия диска не означает, что задача производительности решена.

## Дополнение v4: журнал действий

Механизм v4 сохраняет сжатые снимки v3 и добавляет защищённый журнал изменений. Исторические замеры выше относятся к v3 без нового журнала. Audit использует компактные проекции и одно событие на batch; новые события всё равно увеличивают базу, автоматического удаления нет. Миграция поддерживает v0–v3; точные границы и новое expectedVersion API — [AUDIT-AND-EDITS.md](AUDIT-AND-EDITS.md).

Повтор 24.10 на v4 **с пустым журналом**: 20 058 112 байт (55,10% меньше v2) и 20 017 152 байт (35,31%), исходные поля jobs/rowid совпали. Скрипт явно выводит targetSchemaVersion и auditEvents=0; объём журнала реальной работы этим не измерен.

Текущая v5 добавляет индексы очереди/устройств, не меняя формат снимков. В нагрузочном профиле 100 000 jobs + 20 000 audit + 3380 устройств закрытый файл занял 96 714 752 байт; это отдельный синтетический состав, не норма на операцию и не прогноз данных пользователя. Методика — [LOAD-TESTING.md](LOAD-TESTING.md).

## Дополнение: WAL и online backup

При копировании работающей WAL-базы read snapshot удерживает нужные WAL-страницы до завершения copy. Потребление места временно увеличивается; штатный checkpoint может затем переиспользовать файл без немедленного физического уменьшения его длины. Размер main, выделенного WAL и отдельных backup-пакетов нужно учитывать раздельно. Стенд непрерывной нагрузки/восстановления и его границы описаны в [SOAK-TESTING.md](SOAK-TESTING.md); история автоматически не удаляется.
