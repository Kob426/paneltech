# Ошибки хранения, связи и протокола

Проверено 24.10.2026 в Linux. Речь о сохранении заданий/результатов PanelTech и журнала агента. Система не загружает обновления FACEIT или игры. Симуляция не подтверждает работу Windows QoS.

## Если сервер не может сохранить данные

SQLite full, read-only, busy/locked, I/O, corruption и невозможность открыть файл распознаются по числовому коду SQLite. Ошибка не выдаёт SQL, пути, содержимое записей или credentials. Сервер приостанавливает операции до перезапуска; API, включая `/api/health`, отвечает HTTP 503 с `storage_unavailable`. Ошибка таймера симулятора также приостанавливает операции, не приводит к необработанному исключению процесса. Даже временная блокировка требует проверки и перезапуска: автоматического повтора изменяющей операции нет.

Группа создаётся целиком либо не создаётся. Heartbeat/смена boot/сверка/delivery сохраняются одной транзакцией. Результат и факты устройства сохраняются вместе. DEMO-исполнение, reboot, сверка, отзыв устройства и смена доступа сотрудника также защищены транзакциями. SQLite при некоторых ошибках сам откатывает транзакцию; код не пытается безусловным ROLLBACK скрыть первичную ошибку.

Панель при HTTP 5xx показывает потерю подтверждённой связи и последний загруженный снимок. Потерянный ответ на POST не означает ни успех, ни гарантированный отказ: после восстановления нужно проверить историю. Автоматически повторять применение панель не будет. Если диск недоступен, записать туда новый статус ошибки невозможно — до восстановления API не объявляет сохранённый результат успешным.

## Если агент не может сохранить журнал

Порядок остаётся таким: сохранить receipt → выполнить действие → сохранить результат → отправить → проверить подтверждение → сохранить delivered. Ошибка записи/Flush/rename identity или receipts завершает Worker с кодом 1, а не попадает в повтор сетевого запроса. Старый целый файл сохраняется; оставшийся `.tmp` не считается подтверждённой записью.

- Ошибка до сохранения receipt: действие не начинается.
- Ошибка сохранения результата после действия: сервер не получает несохранённый результат. После устранения причины и рестарта старый receipt без результата становится unknown, повторное изменение запрещено.
- Ошибка сохранения delivered после подтверждения: на диске остаётся недоставленный результат. После рестарта повторяется его отправка, не само действие.
- Потерянный ответ HTTP: outbox остаётся недоставленным. Повторная передача результата идемпотентна на сервере.

HTTP 200 сам по себе не закрывает outbox. Подтверждение обязано содержать совпадающие `id`, `deviceId`, `bootId` и сохранённый результат в состоянии succeeded/failed/expired/unknown. Пустой, повреждённый ответ, чужое задание или running не считаются подтверждением. Сервер может уже сохранить результат: его повторная отправка безопасна и не запускает действие заново. HTTP 401/403 останавливает агент, автоматической регистрации нет.

## Некорректные ответы и часы

Неверные JSON/типы, чужой device/boot, невалидный job UUID не должны начинать действие или загрязнять журнал чужой записью. Некорректные параметры допустимо адресованного задания отклоняются локально: неизвестная операция, exe с аргументами/дубликатами, недоступный DSCP, неверная игра/TTL. Проверяются массивы разрешённых вариантов и ответ регистрации до сохранения токена. В логах остаются только безопасные коды/типы, не тело ответа.

Ошибка исполнителя после начала dispatch трактуется как неизвестный результат: нельзя заявлять «валидация отклонила, изменений не было». Некорректный результат исполнителя преобразуется в unknown (в dry-run — failed), не в технический успех.

До действия используются serverTime и монотонное время ожидания; рассинхронизация свыше 60 секунд запрещает выполнение. Если во время действия часы скачут больше чем на 60 секунд относительно монотонного времени либо истекает TTL, результат становится unknown с `clock_changed` или `expired_during_execution`. Это не отменяет уже произведённые изменения и не запускает их повторно; нужна отдельная инспекция. Часы сервера всё ещё должны синхронизироваться: полноценная защита от ложного времени сервера или всех малых корректировок не реализована.

## Порядок восстановления

1. Остановить панель/агент. Не удалять БД, WAL/SHM, identity, receipts или ownership ради повторного выполнения.
2. Проверить диск, права, блокировки и состояние носителя. Сохранить согласованную защищённую копию; для доступной работающей SQLite использовать `db:backup`, при необходимости `--out` на другой исправный носитель. Файлы БД/агента содержат конфиденциальные данные.
3. Для доступной БД выполнить `npm run db:check -- --db <точный-путь>`. При повреждении использовать проверенный backup и восстановление в новый файл по [BACKUP-RESTORE.md](BACKUP-RESTORE.md). Старую базу не перезаписывать.
4. После устранения причины перезапустить сервер и войти в панель; проверить историю перед новой командой. Для агента сохранить прежнюю согласованную identity/receipt историю. Утрату/повреждение журнала разбирать вручную, не заменять пустым.
5. Unknown разбирать отдельной инспекцией. Она может подтвердить совпадение или несовпадение правил без повторного применения. Реальный агент/Windows-проверка требуют отдельно разрешённой лаборатории; сейчас реальные ПК не подключаются.

## Что проверено и что осталось

`tests/resilience.test.ts` — десять новых Node-тестов. SQLite действительно возвращает SQLITE_FULL при искусственном `max_page_count`; отдельно проверен query_only. Ошибки в отдельных точках записи вводятся контролируемо: batch, poll/delivery, result, DEMO, reboot/сверка, revoke. Проверены rollback, 503/health, сохранность исходных записей, restart и идемпотентная повторная доставка результата. Это не физическое заполнение системного диска.

`tests/agent_recovery.py` — 31 process-тест (12 новых), включая недоступный временный путь записи, ошибки до/после действия и после ack, неверный ack/параметры/доставка, executor exception, скачки часов и TTL во время действия. Используются настоящий .NET Worker, временные файлы и отдельный файловый имитатор. 24 self-test и Linux dry-run с настоящим loopback API проверяют контракт; детали — [AGENT-RECOVERY-TESTS.md](AGENT-RECOVERY-TESTS.md).

Не проверены физический отказ носителя/питания, Windows ACL/NTFS/SCM, реальный NetQos/откат/ownership/UWF, внешний TLS и MikroTik. Контролируемые ошибки и Linux-файлы не доказывают эти свойства. Не заявляется исчерпывающее покрытие всех ответов/отказов. Журнал административных изменений, защита одновременных правок и нагрузка 50+ клубов — следующие отдельные блоки.

## Потеря credentials/state после 4.37

Новый агент сохраняет кандидат до POST регистрации/смены и подтверждает его после lost response/ошибки promotion. Потеря identity/journal/manifest требует явного admin grant и локального --recover-file/--confirm-state-reset с карантином, а не удаления state/нового enrollment. Неполный план блокирует запуск; commandEpoch не допускает старый outbox после восстановления. Подробности — [AGENT-ACCESS.md](AGENT-ACCESS.md). Это не проверка Windows ACL/UWF/носителя.

## Автоматические копии 4.38

Новое расписание, защищённая очистка и отдельная проверка восстановления описаны в [OPERATIONS.md](OPERATIONS.md). Ошибка новой копии не удаляет прежние; lock после аварии не снимается автоматически. Если диск статуса доступен, ошибка сохраняется для следующего старта. При общем latch Store расписание и ручной backup не запускаются; admin GET статуса остаётся доступен только при читаемой БД и действующей сессии. Ни успешная копия, ни GET не снимают latch и не повторяют команды. Worker имеет 120-секундный предел; при аварии `.partial-*`/`.drill-*` разбираются вручную, после проверки завершения процесса. Не стирайте каталог целиком.
