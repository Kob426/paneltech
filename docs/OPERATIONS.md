# Автоматические копии и состояние сервера

Блок 4.38 закрывает локальную автоматизацию части 7.6. Работает в DEMO, личном режиме и отдельно настроенном PILOT; не подключает ПК и не включает реальные операции. Настоящие Windows, защита носителя и внешний мониторинг этим не проверены.

## Запуск и настройки

Обычный запуск остаётся прежним:

```sh
npm ci
npm run demo
```

Для личных аккаунтов сначала `npm run setup:owner`, затем `npm run local`. После входа администратором откройте вкладку **«Сервер»**. Сотруднику с ролью operator она недоступна.

Автоматические копии включены по умолчанию. Если проверенных копий ещё нет или срок истёк, первая попытка начинается через **60 секунд после запуска**. Затем — каждые **6 часов после окончания попытки**, только пока API работает. Остановка сервера останавливает расписание; отдельная ОС-служба/cron не устанавливается. Перезапуск учитывает время прежней успешной копии и не создаёт её раньше срока. Серия запусков короче минуты не гарантирует копию — используйте кнопку перед важными изменениями.

| Переменная | По умолчанию | Допустимые значения |
| --- | --- | --- |
| `AUTO_BACKUP` | `1` | `0` выключает расписание, ручная кнопка остаётся |
| `BACKUP_INTERVAL_MINUTES` | `360` | целое 5–10080 |
| `BACKUP_KEEP` | `7` | целое 2–100 |
| `BACKUP_MAX_MIB` | `1024` | целое 16–1048576; бюджет пакетов, МиБ |
| `BACKUP_DIRECTORY` | `backups` рядом с файлом БД | локальный каталог; для каждой БД создаётся отдельный подкаталог |

Настройки читаются при запуске; неверные числа останавливают запуск до открытия БД. Для примера в Bash:

```sh
AUTO_BACKUP=1 BACKUP_INTERVAL_MINUTES=360 BACKUP_KEEP=7 BACKUP_MAX_MIB=1024 npm run local
```

PowerShell:

```powershell
$env:AUTO_BACKUP='1'
$env:BACKUP_INTERVAL_MINUTES='360'
$env:BACKUP_KEEP='7'
$env:BACKUP_MAX_MIB='1024'
npm run local
```

Windows-выполнение этих настроек не проверено здесь. Для отключения расписания задайте `AUTO_BACKUP=0`, затем перезапустите API. История заданий в рабочей БД при очистке копий **не удаляется**.

## Формат и место

По умолчанию копии `.data/local.sqlite` находятся в `.data/backups/automatic-<ключ>/backup-<UTC-дата>-<UUID>/`. Ключ — первые 16 hex SHA-256 абсолютного пути к исходной БД; это изоляция каталогов, не шифрование и не идентификатор физического носителя. Для DEMO и PILOT используются другие файлы/каталоги. После перемещения checkout старый каталог не усыновляется автоматически.

Один пакет содержит:

- `backup.sqlite` — самостоятельная SQLite с DELETE journal, без зависимости от WAL источника;
- `manifest.json` — версия схемы, размер, SHA-256 и режим;
- `automatic.json` — метка расписания, источник и результат проверки восстановления.

В родительском каталоге находятся `.owner.json`, ограниченный по размеру `.status.json` и, пока идёт работа, `.running.lock`. Отдельная БД мониторинга/растущая история замеров не создаётся. Данные и сжатые снимки сохраняются в исходном SQLite-формате; дополнительного gzip и новых зависимостей нет. В Linux новые каталоги создаются с 0700, файлы копий/метаданных — 0600. ACL на Windows требуют отдельной проверки.

Копия содержит пароли в виде хешей, сеансы/токены и историю исходной БД. Шифрования копий здесь нет. Каталог должен быть защищён правами ОС и при необходимости шифрованием диска. Панель не скачивает копии, не принимает пути назначения и не возвращает абсолютные пути/секреты в статусе. Копия на том же диске не защищает от поломки или потери диска: перенос на отдельный защищённый носитель настраивается оператором отдельно. Внешняя загрузка в этой реализации отсутствует.

## Что считается успешной копией

1. API запускает отдельный Node/tsx-процесс с конфигурацией через IPC, без shell и передачи окружения с паролями. Проверки SQLite и восстановление не выполняются в основном JS-потоке API.
2. Единственный lock запрещает одновременное копирование в один управляемый каталог. Проверяется принадлежность каталога; ссылки в пути отклоняются. Сторонний непустой каталог автоматически не принимается под очистку.
3. Существующий online-backup удерживает согласованный read snapshot WAL. Пишущий API продолжает работу. Пакет публикуется после integrity/schema/SHA-проверок; штатный copy-step ограничен 30 секундами, весь дочерний процесс — 120 секундами.
4. Копия восстанавливается в **новый временный файл**. Проверяются SQLite/схема, количество jobs/audit/users/clubs/games, отсутствие сеансов/регистрационных разрешений и действующих токенов, отсутствие queued/running. Очередь становится expired/unknown по прежней политике восстановления. API/симулятор/агент для этой временной БД не запускается.
5. Временная восстановленная БД удаляется. Только после этого копия получает метку успешной автоматической проверки и начинается retention. Рабочая БД не заменяется; настоящее восстановление остаётся явным действием администратора.

Отметка в панели означает успешную проверку **на указанное время**. Она не является непрерывной проверкой носителя: ручное удаление/повреждение пакета после проверки обнаружится при следующем проходе. Показанные число и объём относятся к последней проверке, не к текущей независимой инвентаризации файловой системы.

## Ограничение хранения

После новой успешной копии старые проверенные пакеты удаляются от самых старых, пока не выполняются оба условия: число не больше `BACKUP_KEEP`, сумма размеров файлов пакетов не больше `BACKUP_MAX_MIB`. Последняя пригодная копия сохраняется **всегда**, даже если она одна больше бюджета; панель показывает превышение.

Удаляются только обычные каталоги с ожидаемым именем, точным комплектом трёх файлов, меткой данного расписания и повторно проверенным manifest/SHA/SQLite. Ручные backup, повреждённые пакеты, посторонние файлы, символьные ссылки и незавершённые `.partial-*` / `.drill-*` автоматически не удаляются. Их количество показывается как требующее ручного разбора; их место не входит в объём проверенных пакетов. Бюджет не является жёсткой дисковой квотой и не учитывает блоки ФС.

Для создания новой копии и временного восстановления нужно дополнительное место сверх сохранённых копий: ориентировочно две полные БД плюс WAL/временные файлы и запас под запись. Старая копия не удаляется заранее ради свободного места. При отказе новой копии прежние проверенные копии сохраняются, видна ошибка. Диск/питание/вредоносная замена файлов в процессе проверки физически здесь не проверялись; владелец каталогов считается доверенным.

## Состояние и ошибки

Во вкладке «Сервер»: разрешены ли операции или сработала остановка записи, размеры БД/WAL, свободное место на диске БД, память API, расписание, последняя попытка/успех, результат восстановления и предупреждения очистки. API-статус дополнительно отдаёт uptime в секундах. Свободное место отдельного носителя `BACKUP_DIRECTORY` в этой метрике не измеряется. `ready` означает отсутствие latch остановки; это не гарантия следующей записи и не полный SMART/health-check оборудования.

- `backup_failed`: ошибка чтения/места/прав/целостности или восстановления. Текст исключения/содержимое БД не возвращается. Ошибка обслуживания/метаданных может возникнуть уже после публикации нового пакета; перед повтором проверьте каталог.
- `backup_locked`: активный процесс или незавершённая блокировка. Блокировка автоматически не снимается, PID автоматически не переиспользуется для решения об удалении.
- `worker_failed`: дочерний процесс завершился/превысил timeout без результата. Ошибка сохраняется, если каталог статуса доступен для записи.
- `status_invalid`: метаданные прежнего состояния не прочитаны; прежний успех не угадывается. Новая успешная попытка собирает инвентарь заново.

При общей ошибке хранилища Store останавливает обычные API/таймер очереди; новые копии через расписание/кнопку не запускаются. Уже начатое read-only копирование может завершиться. GET статуса работает через SELECT без записи/очистки сеансов, если БД читается и существующая сессия администратора не истекла. При полностью недоступной/повреждённой БД статус авторизовать невозможно — понадобится терминал. Успешный GET не сбрасывает latch и не возобновляет задания.

После пропавшего ответа POST **не нажимайте повторно сразу**: обновите статус и дождитесь текущего результата. Кнопка запускает asynchronous job и отвечает 202, не означает готовую копию. Работающая копия блокирует повторный запуск 409. Секреты и реальные пути не пишутся в сообщения ошибок; stdout содержит только код ошибки. При недоступном диске нельзя гарантировать сохранение даже `.status.json`.

Если осталась `.running.lock`: остановите API и убедитесь, что отдельный процесс `server/backup-task.ts` тоже завершён. Сохраните БД/WAL и имеющиеся пакеты. Только после проверки отсутствия копирования вручную уберите эту блокировку; отдельно разберите `.partial-*` / `.drill-*`. Не удаляйте lock работающего процесса и не очищайте весь каталог. Исправьте место/права/носитель, перезапустите API и создайте новую проверенную копию. Безопасный выбор файла/переключение БД — [BACKUP-RESTORE.md](BACKUP-RESTORE.md).

## API и проверки

- `GET /api/admin/operations` — действующая cookie-сессия администратора; no-store; ограниченный статус без путей/токенов. Доступен при latch остановки записи, пока возможно чтение авторизации.
- `POST /api/admin/operations/backup` с `{}` — admin + CSRF/Origin, только разрешённый сервером каталог; 202 accepted / 409 busy. Запрос фиксируется в журнале `backup.requested`; результат находится в статусе копирования. Автоматические циклы не создают растущий журнал в основной БД.
- Веб-восстановления поверх рабочей БД и удаления пакетов по произвольному пути нет. Используйте `db:verify` и `db:restore -- --from <пакет> --to <новый-файл>` из инструкции восстановления.

`npm test` включает 15 новых файловых/процессных/API-проверок: retention, последний пригодный пакет, corruption/foreign/symlink/partial, lock, ошибка/kill и restart, отдельный restore, очередь/доступ, роли/CSRF/пауза записи. `npm run test:browser` включает `browser_operations.py`: desktop/mobile, настоящий backup/restore, lost response без повтора, настоящий lock/исправление, stale GET/блокировка кнопки, права и тёмный контраст.

`npm run test:operations` — отдельный временный DEMO на loopback 3114: **настоящий 60-секундный таймер**, продолжающиеся GET API, автоматически созданный/восстановленный пакет, точный CLI verify и restart без преждевременной второй копии. Включён в локальный `scripts/check-web.sh`. Используется только временная БД; реальный диск целиком не заполняется. Исходные результаты/границы — [OPERATIONS-CHECKS.json](OPERATIONS-CHECKS.json), [PROJECT-STATUS.md](../PROJECT-STATUS.md).

Открыты: отдельный носитель/off-site, шифрование/ключи/уведомления дежурному, внешнее наблюдение за остановленным API/ОС, Windows ACL/NTFS/SCM/питание, многочасовая нагрузка расписания, окончательный review реального TLS/Host/proxy и защита инфраструктуры. Эти части 7.6 не закрыты успешными Linux-тестами.

Новый отдельный стенд совместной нагрузки и автоматического расписания — [AUTOMATIC-LOAD.md](AUTOMATIC-LOAD.md). Его результат учитывается отдельно от функциональных проверок блока 4.38; SHA старого OPERATIONS-CHECKS.json не переписываются после добавления npm-команды стенда.
