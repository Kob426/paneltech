# Нагрузка и очередь: воспроизводимый Linux-стенд

Блок выполнен в облачной среде Codex на временных синтетических данных. Windows, PowerShell, UWF, MikroTik и клубные ПК не используются. API слушает только случайный loopback-порт, после теста процесс завершается, временные БД удаляются. Продукт/тестовый сервер не публикуется.

## Повторить

Нужны Linux, Node.js 24, Python 3 со стандартной библиотекой и `npm ci`. Нагрузочный runner использует POSIX pipes/select; Windows-версия стенда не реализована. Это ограничение измерительного скрипта, не отдельная зависимость запуска панели. Из папки проекта:

```sh
npm run measure:load
# Только совместный профиль, 100 000 завершённых заданий:
npm run measure:load -- --jobs 100000 --phases http-mixed
# Разобрать фактическое время и планы SQL-запросов чтения:
npm run measure:load -- --jobs 100000 --phases profile-reads
```

Скрипт печатает JSON-строки с результатами и итоговым объектом. Он не принимает путь к БД или адрес сервера и не использует ваш `DB_PATH`. Worker требует специальный маркер в собственном временном каталоге. Тестовые аккаунты/токены генерируются только для этого стенда и в результаты не выводятся. Бинарник Windows-агента и `--enable-qos` не запускаются.

Полный прогон может занять несколько минут: подготовка данных и проверка при открытии базы выполняются отдельно для каждого процесса. Тайм-аут не считается успешным результатом.

## Что измеряется

Два профиля: **52 клуба × 65 ПК = 3380 устройств**, 10 000 и 100 000 завершённых заданий, ещё 52 старых unknown (по одному на клуб), 2000/20 000 событий audit. Шесть тестовых сотрудников, пять exe/правил в снимке, произвольные имена ПК и стабильные UUID. Это выбранный синтетический профиль, а не выгрузка данных пользователя.

| Фаза | Работа |
| --- | --- |
| expire | Три проверки сроков при отсутствии истёкших активных команд |
| poll-idle | Три выдачи для ПК без новой команды |
| create65 | Одно создание группы: 64 queued и один failed/busy из-за старого unknown |
| tick | Один heartbeat/tick всех 3380 DEMO-ПК без новых команд |
| tick64 | Одно DEMO-исполнение 64 команд; ещё один tick проверяет отсутствие повтора |
| http-read | Шесть последовательных клиентов, всего 120 чтений state/history выбранных клубов |
| http-heartbeat | 32 клиента, один раунд из 3380 HTTP poll по индивидуальным тестовым токенам |
| http-mixed | Те же шесть клиентов чтения и 32 клиента heartbeat стартуют одновременно: 3500 запросов |

В HTTP heartbeat `inspectionVerified=false`, новых команд нет: пустой/симулированный набор не выдаётся за подтверждение маркировки. Отдельный tick64 выполняет файлово-независимую серверную **DEMO-симуляцию**, без Windows. Неопределённые старые задания остаются заблокированными.

Core-фазы используют фиксированные часы, чтобы истечение срока/переход офлайн во время медленного исходного кода не меняли размер сравниваемой работы. HTTP-фазы используют прошедшее реальное время относительно времени генерации. В Core-фазах сравнивается SHA-256 старой истории, новые задания проверяются отдельно, повторное исполнение запрещено. Настоящие TTL/boot/ошибки проверяет отдельный набор regression tests.

## Границы замера

- Один Node API-процесс и локальная SQLite, обычные WAL/транзакции и проверки целостности. Надёжность записи не отключалась ради ускорения.
- Источник перед фазой закрыт; каждая фаза получает отдельную копию одной синтетической БД. История пользователя не затрагивается. После тайм-аута останавливается только собственный worker.
- `timesMs` — непосредственно вызов Core; create65 не включает HTTP/логин/audit, tick64 не включает подготовку команды. `startupMs` — открытие/проверка Store, а не весь запуск Node/npm.
- Core-worker имеет лимит 30 секунд вместе с открытием БД/подготовкой. HTTP-поток имеет окно 20 секунд **после** открытия Store и логина. Если его не хватает, оставшиеся соединения прерывает стенд: эти ошибки после остановки не означают отдельный отказ сервера/маркировки. Процентили неполного прогона нельзя использовать как успешный SLA.
- HTTP latency измеряется клиентом и включает TCP, очередь, обработку и JSON. Используется стандартный urllib с новыми соединениями; это не точная модель keep-alive .NET HttpClient.
- `maxRssMiB` — максимальный RSS дочернего Node-процесса, включая открытие БД, проверку и работу; `memoryStartMiB` — максимальный RSS к моменту начала, не гарантированная текущая память. Heap/GC отдельно не стабилизировались. RSS Python-клиентов в число не входит.
- Event-loop delay измеряется Node монитором с шагом 10 мс; это диагностический показатель, не задержка пакета/сети.
- Нет искусственного сброса файлового кеша ОС и гарантии выделенного CPU. Указаны отдельные измеренные прогоны, без статистического доказательства производственной ёмкости.

## Что изменено в коде

`server/queue-queries.ts` отделяет запросы очереди и устройств. Схема **v5** добавляет четыре индекса: активные задания конкретного ПК, сроки queued/running, устройства клуба и индивидуальный token hash. Терминальные задания не входят в два индекса очереди. Время перехода queued→expired / running→unknown и правила блокировки unknown сохранены.

Core.create проверяет занятость через EXISTS; poll читает только активные/следующую команду своего ПК; expire выбирает только достигшие срока queued/running. Poll обновляет сроки своего устройства; глобальные state/history/tick по-прежнему обрабатывают все достигшие срока задания. Reboot, сверка и revoke не сканируют завершённую историю. Выдача сохраняет порядок вставки (rowid), не сортировку по произвольной дате.

DEMO heartbeat обновляет временные метки одной транзакцией через JSON_SET, не распаковывая правила и не меняя boot/inspectedAt/снимки. В исполнение попадают только DEMO-ПК с queued; offline/revoked/протокольные устройства пропускаются. Завершённые команды не исполняются повторно.

Планы SQLite проверены: эвристика могла выбирать полный индекс успешных заданий или records вместо нужного частичного индекса. Для горячих запросов применён INDEXED BY. Поиск последних операций/успехов/«помогло» рабочего экрана ограничен индексом выбранного клуба, а active — индексом активных заданий. Полная история остаётся доступна через страницы.

Открытие уже актуальной схемы полностью проверяет её один раз и не берёт ненужную write-транзакцию/повторные проверки. Миграции старых схем всё ещё выполняются транзакционно. v4→v5 создаёт только индексы, не переписывает records/rowid, снимки или audit. Перед обновлением остановите API и выполните `npm run db:migrate -- --db .data/local.sqlite` с проверенным backup.

## Изменение state API

`GET /api/state?clubId=...&gameId=...` теперь возвращает подробные устройства **выбранного клуба**. Все клубы сохраняются в `clubs` со счётчиками `deviceCount`/`onlineCount`; sidebar использует эти счётчики. Токены не выдаются. Поиск/карточка/массовый выбор текущего клуба сохранены. Старый `GET /api/state` без clubId сохраняет выдачу всех устройств для совместимости и не является ограниченным по размеру ответом.

Клиентам, которые читали другие клубы из scoped `devices`, нужно перейти на счётчики или запросить нужный клуб. Числа байтов в замере относятся только к заданному профилю: большие реальные наборы правил, комментарии и незавершённые задания могут увеличить ответ.

## Результаты и оставшаяся работа

Числа и исходные метрики сохраняются в [LOAD-RESULTS.json](LOAD-RESULTS.json). Сравнивается замороженная локальная копия кода v4 до изменений с текущим кодом v5, без обращения к GitHub. Контрольный HTTP-клиент, количество данных и параллельность одинаковы. Источники Core/API/SQL и клиентского драйвера идентифицируются SHA-256 в отчёте.

Это проверка коротких контролируемых нагрузок, а не допуск к 52 реальным клубам. Не проверены длительный soak/рост WAL и памяти за сутки, поддержание заданного открытого QPS при двухсекундном polling всех агентов, внешний TLS/интернет, одновременный backup с такой нагрузкой, миллионная история/глубокий OFFSET и несколько API-процессов. Windows/QoS/SCM/UWF/MikroTik и оборудование пользователя остаются отдельными этапами. Автоматического удаления истории/журнала не добавлено.

## Дополнительная непрерывная проверка

Отдельный стенд `npm run measure:soak` задаёт частоту запросов на 10 минут и проверяет два online-backup/restore при записях. Методика и фактические результаты — [SOAK-TESTING.md](SOAK-TESTING.md). Он не заменяет сравнение до/после выше: другой профиль и длительность. Полная частота всех агентов каждые 2 секунды, сутки работы, внешняя сеть/TLS и Windows по-прежнему отдельно.

После блока доступа агентов 4.37 сервер/core изменены. Зафиксированные выше цифры относятся к прежним SHA источников в JSON-отчёте; нагрузка в 4.37 не перемерялась. Старые метрики/хеши сохранены как историческое доказательство, а не замена проверки новой версии.

Блок 4.38 добавил расписание/отдельный worker и restore-drill каждой копии. Этот новый профиль под прежней массовой нагрузкой ещё не перемерялся; исторические JSON/SHA не заменяются текущими тестами таймера и восстановления.
