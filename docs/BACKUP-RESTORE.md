# Резервная копия и восстановление PanelTech

Команды выполняются из папки проекта с Node.js 24 и установленными зависимостями (`npm ci`). Для личного режима база по умолчанию `.data/local.sqlite`, для открытого DEMO — `.data/demo.sqlite`. Если сервер запущен с другим DB_PATH, явно укажите этот же путь. Команды не выбирают исходную базу по окружению и не создают её при опечатке в пути.

## Копирование работающей базы

```sh
npm run db:check -- --db .data/local.sqlite
npm run db:backup -- --db .data/local.sqlite
```

Останавливать панель ради backup не требуется. Используется SQLite Online Backup API через отдельное read-only соединение, с учётом WAL. Обычное копирование одного работающего `.sqlite` файла небезопасно: последние записи могут находиться в WAL.

Backup выводит JSON с `ok`, `path`, `schemaVersion`, `records`, `sha256`. В `.data/backups/backup-<дата>-<UUID>/` создаются:

- `backup.sqlite` — самостоятельная база в DELETE journal mode, без зависимости от исходных WAL/SHM;
- `manifest.json` — версия формата/схемы, время завершения, количество записей, режим, размер и SHA-256 файла.

Другой каталог: `npm run db:backup -- --db .data/local.sqlite --out .data/my-backups`. Каждая копия получает новое имя; существующие копии не перезаписываются и автоматически не удаляются. Сначала всё создаётся в закрытом `.partial-…`, проверяется, сбрасывается на диск и только затем публикуется переименованием каталога. Обычная ошибка удаляет свой временный каталог; после SIGKILL/потери питания `.partial-…` может остаться, готовой копией он не считается.

Во время записи другим соединением SQLite может перезапускать копирование для согласованности. На шагах проверяется лимит 30 секунд; это не абсолютный таймаут зависшей файловой системы. При сбое создайте новую копию после устранения причины, исходная база остаётся рабочей.

## Проверка копии

Скопируйте **реальный путь из поля `path`**, вместо примера ниже:

```sh
npm run db:verify -- --from .data/backups/backup-REPLACE-WITH-ACTUAL-NAME
```

Не допускаются посторонние WAL/SHM/journal; файл должен быть самостоятельной DELETE-mode копией. Проверяются манифест, размер/SHA-256, `PRAGMA integrity_check`, поддерживаемая схема/журнал миграций, формат записей и ссылки/целостность общих снимков v3. Содержимое пользовательских записей и credentials не выводится. Это проверка физической целостности и структуры, не полная проверка бизнес-связей и не подтверждение Windows QoS.

База и манифест должны переноситься вместе. SHA-256 обнаруживает повреждение, но не заменяет цифровую подпись: используйте только доверенные копии. Копии не зашифрованы и содержат историю, аккаунты/хеши паролей и другие конфиденциальные данные. В Linux новый каталог имеет mode 0700, файлы 0600; Windows ACL здесь не проверены. Храните отдельную копию на другом защищённом носителе. GitHub/публичные сервисы для этого не используются.

## Восстановление в новый файл

```sh
npm run db:restore -- --from .data/backups/backup-REPLACE-WITH-ACTUAL-NAME --to .data/recovered.sqlite
npm run db:check -- --db .data/recovered.sqlite
```

Команда требует новый путь. Существующий файл, ссылка, WAL/SHM/journal с таким именем вызывают отказ. Рабочая база не заменяется, DB_PATH сервера не меняется, сервер и реальные ПК не запускаются.

После проверки пакета копия создаётся во временном файле рядом с назначением; SHA-256 проверяется повторно. Поддерживаемая старая схема мигрирует только в этом файле. Затем одной транзакцией:

- аккаунты/роли/отключения, клубы, каталог, стабильные device ID, завершённые результаты и отметки «помогло» сохраняются на момент копии;
- browser sessions и enrollment удаляются: все сотрудники входят заново;
- queued становится expired, running — unknown, прежний unknown остаётся unknown и требует новой сверки; команды не переотправляются;
- наблюдения устройств помечаются устаревшими; у DEMO новая boot-сессия и удалены собственные правила симулятора;
- токены реальных устройств удаляются, устройства отзываются. Их повторное доверенное подключение требует отдельной процедуры пилота, сейчас не автоматизировано.

Логическое содержимое завершённых снимков заданий/отметок сохраняется; физический JSON старой схемы может измениться при миграции в v3. Восстановленные аккаунты используют пароли/отключения **на момент копии**; изменения доступа после неё не сохраняются. Перед возвращением реальной команды в работу доступы нужно сверить отдельно.

Новый файл публикуется атомарным hard link без перезаписи. Если файловая система не поддерживает эту операцию, восстановление завершится ошибкой. Сбой последнего fsync каталога может оставить уже готовый новый файл: проверьте его через `db:check`, не заменяйте старую базу вслепую. Linux-процедура проверена; Windows/сетевые диски/потеря питания не проверены.

## Проверить личную восстановленную панель

Остановите прежнюю панель Ctrl+C. Сохраните оригинал и пакет копии. В отдельном терминале запустите восстановленный личный DEMO:

Linux/macOS shell (фактически проверено в Linux):

```sh
DB_PATH=.data/recovered.sqlite npm run local
```

PowerShell (команды подготовлены, выполнение на Windows ещё не проверено):

```powershell
$env:DB_PATH = '.data/recovered.sqlite'
npm run local
```

Войдите своим логином, проверьте сотрудников, каталог, историю и отметки. Старые сеансы не должны действовать. Успешная запись в истории не подтверждает текущее назначение правил; unknown требует сверки. Для открытого DEMO вместо `local` используется `demo`. Восстановленная pilot-база специально не допускается к запуску в DEMO; реальный пилот этим блоком не разрешён.

Переменная DB_PATH действует в текущем окне терминала. Для возвращения к исходной базе остановите процесс и откройте новый терминал без этой переменной либо явно задайте путь оригинала. Не запускайте два API/симулятора поверх одной базы. Старую базу и копию не удаляйте до проверки восстановленной версии.

## Версии схемы и миграции

- v0 — прежняя неверсионированная `records(kind,id,data)`; при регистрации v1 значения и rowid не меняются.
- v1 — зарегистрированная схема records и `schema_migrations`.
- v2 — четыре индекса заданий для фильтров/страниц.
- v3 — общие сжатые снимки exe/правил; логические значения и rowid истории сохраняются. Старые поддерживаемые копии v0–v2 читаются и мигрируют только в новом файле при restore.
- v4 — append-only audit records, индекс и три защитных триггера; старые данные/rowid шага v3→v4 не переписываются.
- v5 (текущая) — четыре индекса очереди/устройств; шаг v4→v5 сохраняет records/rowid/snapshots/audit без преобразования данных.

`PRAGMA user_version` и журнал миграций проверяются на соответствие. Шаги выполняются в одной транзакции: при ошибке откатываются DDL, версия и журнал. Новая/чужая/повреждённая схема, неверный JSON/id, посторонние triggers/views или отсутствие штатной защиты audit или несогласованный журнал отклоняются. Downgrade не выполняется.

Store применяет поддерживаемые миграции при старте, но **автоматически не делает отдельную копию**. Перед обновлением программы предпочтителен явный путь: остановить API, установить зависимости, выполнить:

```sh
npm run db:migrate -- --db .data/local.sqlite
npm run local
```

`db:migrate` сначала создаёт и проверяет backup старой схемы. Если backup не удался, миграция не начинается. Команда работает только с уже существующей поддерживаемой базой. Предыдущую версию программы не запускайте поверх новой схемы. Для отката понадобятся сохранённые исходники и совместимый старый инструмент восстановления: текущая db:restore мигрирует копию в v5. Оригинальный пакет backup не изменяется. Проверки миграций и разбор legacy-копии делались только на временных данных.

## Размер и уплотнение

`npm run db:stats -- --db .data/local.sqlite` показывает main/WAL/SHM, свободные страницы и размеры уникальных снимков. `db:compact -- --db <исходник> --to <новый-файл.sqlite>` сначала делает backup, затем **новую восстановленную копию** с VACUUM/сохранением rowid. К ней применяются перечисленные выше отзыв сеансов/токенов и expiry/unknown; старые команды не выполняются. Источник не заменяется. Порядок безопасного переключения, временное место и синтетические замеры — [ECONOMICAL-STORAGE.md](ECONOMICAL-STORAGE.md).

Нагрузку 50+ клубов этот блок не подтверждает.

## Backup при непрерывных записях — исправление 24.10.2026

Нагрузочная проверка выявила: incremental backup мог постоянно начинаться заново при внешних commit и достигать timeout 30 секунд. Теперь исходное read-only соединение начинает read transaction **до** integrity/schema check и удерживает согласованный WAL snapshot до завершения SQLite-copy. Затем reader освобождается до проверки/хеширования/публикации назначения. При ошибке reader закрывается, staging удаляется; тайм-аут не увеличен и проверки не отключены.

Копия отражает состояние на начало read snapshot; более поздние изменения остаются в рабочей базе и войдут в следующий backup. API не останавливается. Удержание reader временно мешает checkpoint очистить необходимые WAL-страницы, поэтому WAL может вырасти на время копирования. Не запускайте неограниченное число параллельных backup. Это гарантия для рабочего WAL-режима; старые закрытые DELETE-базы копируются прежними CLI-командами, непрерывная работа writer на них не проверялась.

Методика, реальный неудачный запуск и повторная проверка — [SOAK-TESTING.md](SOAK-TESTING.md). Отдельные регрессии подтверждают прогресс copy при commit после каждого шага и освобождение reader после успеха/отказа. Формат manifest/SQLite v5 и процедура восстановления не менялись. Windows/NTFS/SMB, физические отказы диска/питания остаются непроверенными.

## Автоматизация 4.38

По умолчанию сервер теперь делает копии по расписанию (6 часов, первый необходимый запуск через 60 секунд) в отдельный `automatic-<ключ>/` каталог. Перед retention новая копия проходит настоящий изолированный restore-drill. Ручные команды выше сохранены; они не попадают под автоматическую очистку. Статус/запуск — вкладка администратора «Сервер»; бюджет 7 копий/1 ГиБ с сохранением последней пригодной. Формат, точные переменные, файловые блокировки, безопасное восстановление после сбоя и ограничения — [OPERATIONS.md](OPERATIONS.md).

Проверки предыдущих блоков выше исторические. В 4.38 прошли 165 Node-теста, восемь Chromium-сценариев, database CLI/API и отдельный реальный 60-секундный таймер/backup/verify/restore/restart. Старые отчёты LOAD/SOAK и AGENT-ACCESS сохраняют SHA своих проверенных версий; их не переписывают под новый код.
