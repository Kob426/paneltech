# Журнал действий и одновременные правки

Реализовано 24.10.2026, проверка в Linux DEMO. Откройте **Журнал действий** под администратором. Здесь видны автор, время, объект и безопасные значения до/после. Фильтры: сотрудник/агент, действие, даты в часовом поясе браузера; по 25 событий на странице. Новые записи появляются после «Обновить выборку». Оператору журнал недоступен, свои операции/отметки он по-прежнему видит в заданиях и истории.

## Какие события сохраняются

- Создание/изменение игр и клубов: название, exe, ревизия, разрешённые варианты.
- Создание сотрудника, смена роли/доступа и сброс пароля. Сброс содержит только признак изменения пароля.
- Изменение отметки задания: исход, причина, длина комментария и версия отметки. Сам текст комментария остаётся в истории задания и в журнал не дублируется.
- Выдача enrollment, регистрация агента и отзыв. Значения токенов/их хеши не записываются. Повторный отзыв уже отозванного устройства не создаёт второе событие.
- Создание задания: одно событие на batch со ссылкой, игрой, операцией и количеством ПК; полные снимки каждого ПК уже находятся в истории.
- Ручные смена сценария/перезагрузка/сверка DEMO с явным названием симуляции.

Автор назначается из действующей серверной сессии или подтверждённой регистрации устройства. Время назначает сервер. Подставить автора через тело запроса нельзя. Пароли/хеши паролей, cookie, CSRF, enrollment и device token в журнал не включаются. Чтение журнала требует административной роли. JSON в подробностях отображается текстом, без исполнения HTML.

Журнал фиксирует **успешно сохранённые изменения**. Отказы валидации/прав/версии и ошибки сохранения не создают событие успеха. Входы/неудачные попытки входа, автоматические heartbeat/tick, прямые изменения SQLite/CLI и начальное заполнение сейчас не являются событиями этого журнала. Старые действия до внедрения журнала не восстанавливаются задним числом. Это журнал изменений, не полный журнал информационной безопасности.

## Как защищены записи

Механизм SQLite v4 (сохранён в текущей **v5**) хранит события отдельным видом `records.kind='audit'` и добавляет индекс даты и три защитных триггера. Через Store/SQL нельзя обновить, удалить или заменить существующее событие (включая INSERT OR REPLACE). API изменения/удаления событий нет. Проверка схемы требует точные защитные триггеры; удалённые/изменённые или посторонние triggers/views вызывают отказ запуска/проверки.

Изменение данных, отзыв связанных сеансов и запись события выполняются одной транзакцией. Если событие не удалось записать, откатывается само изменение. Успех не отправляется клиенту до COMMIT. Backup/restore сохраняют события; уплотнение не удаляет историю/журнал. Восстановление возвращает состояние на момент копии: события после неё в восстановленном файле отсутствуют.

Защита рассчитана на приложение и обычные SQL-операции. **Владелец файла БД может удалить файл или изменить схему.** Внешнего защищённого хранилища, цифровой подписи/криптографической цепочки и независимой проверки вмешательства нет. Это не доказательство неизменности перед администратором хранилища.

## Если коллега изменил запись раньше

Форма запоминает версию при открытии записи. Периодическое обновление списка не подменяет версию открытого черновика. Сервер внутри транзакции сравнивает её с текущей версией. При несовпадении отвечает HTTP **409 / edit_conflict** и ничего не сохраняет. При отсутствии версии — **428 / version_required**. Автоматической перезаписи/объединения или повтора PUT/POST нет.

Форма игры/клуба, строка сотрудника и форма отметки сохраняют черновик и показывают действие «Загрузить актуальную …». Оно явно заменяет черновик свежей записью; затем можно проверить данные и внести изменения заново. Успешное сохранение одной строки сотрудника не заменяет другие строки списка. Пароли после попытки сброса очищаются и в черновиках не удерживаются. Если сброс столкнулся с конфликтом, закройте окно, загрузите свежие данные сотрудника и начните новую явную попытку.

Потеря ответа тоже не повышает версию черновика автоматически: если сервер успел сохранить изменение, повторная явная отправка старой версии получит конфликт. Сначала проверьте актуальные данные. Сброс пароля и смена роли/доступа разделяют одну версию, поэтому старый сброс не отменяет более новое решение коллеги и не отзывает сеансы при конфликте.

## Контракт API

Изменяющим запросам нужен `expectedVersion` в JSON:

| Запрос | Откуда взять версию |
| --- | --- |
| `PUT /api/admin/games/:id` | `revision` игры из state или `GET /api/admin/games/:id` |
| `PUT /api/admin/clubs/:id` | `version` клуба из state или `GET /api/admin/clubs/:id` |
| `PUT /api/admin/users/:id` | `version` сотрудника из `GET /api/admin/users` |
| `POST /api/admin/users/:id/password` | та же `version` сотрудника |
| `POST /api/jobs/:id/feedback` | `feedbackVersion` задания (для старой записи 0) или `GET /api/jobs/:id/feedback` |

У старых клубов/сотрудников версия по умолчанию 1; при сохранении увеличивается. У отметки отдельный счётчик: он не меняет ревизию игрового каталога в задании и не конфликтует с обновлением технического статуса. Ответы обновления игры/клуба/сотрудника возвращают сохранённую запись с новой версией, без паролей. Старые клиенты без expectedVersion необходимо обновить; обход проверки не предусмотрен. Команды создания задания, регистрации и отзыва не являются редактированием открытого черновика.

`GET /api/admin/audit`: `page`, `snapshot`, `actor` (стабильный ID), `action`, `from`, `to` (миллисекунды epoch). Ответ: `items,total,page,pages,snapshot,actors,actions`. Snapshot фиксирует границу вставок; старые события неизменяемы. Порядок — обратный порядок вставки, не произвольные часы клиента. Actors/actions — справочники всего доступного журнала. Неизвестные параметры/невалидные пределы отклоняются.

## Обновление базы и место

Как и прежде, перед обновлением программы остановите API и выполните `npm run db:migrate -- --db .data/local.sqlite`: команда сохраняет проверенный backup. Поддерживаются старые схемы v0–v4. Шаг v3→v4 не переписывает старые записи/rowid и не придумывает прошлые события. Текущая restore мигрирует копию в v5. Запуск прежней версии поверх v5 не поддерживается.

Журнал находится в той же SQLite, отдельный сервис/тариф не требуется. Сохраняются проекции изменений, а не полная БД/задания/credentials. Сжатие общих снимков v3 продолжает работать, но журнал добавляет новые данные. Замеры экономии для v3 в [ECONOMICAL-STORAGE.md](ECONOMICAL-STORAGE.md) относятся к тем синтетическим профилям без нового журнала; переносить их на весь объём v4 нельзя. Автоматическое удаление журнала/истории и политика retention не добавлены.

## Проверки и ограничения

13 новых Node-тестов: одновременные HTTP-запросы, stale/missing версии, пароли/отзыв сеансов, отметки двух сотрудников, роли/подмена автора/отсутствие секретов, lifecycle устройства без реального ПК, откат при ошибке записи журнала, SQL-защита, страницы/фильтры, миграция v3 и backup/restore. Весь набор — 126 тестов.

`tests/browser_audit.py` использует две независимые сессии администраторов, настоящий API/SQLite на loopback 3108, потерю ответа после COMMIT и ошибки 409. Проверены черновики/явная перезагрузка игры/клуба/сотрудника/отметки, сброс пароля, фильтры журнала, desktop 1512/mobile 390, контраст проверенного текста и отсутствие общего overflow/JS errors. Пять предыдущих браузерных сценариев сохраняются. Это не полный аудит доступности.

Поддерживается один процесс API; длительная производственная ёмкость журнала/очереди и несколько API-процессов не подтверждены. Короткая синтетическая нагрузка 52 клубов проверена последующим блоком: LOAD-TESTING.md. Реальные Windows-операции, служба, UWF, TLS и MikroTik в этот блок не входят. GitHub/Actions и публикация не использовались.
