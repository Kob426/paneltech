# Архитектура и гарантии прототипа

## Компоненты

Один Express API обслуживает собранную Vue-панель. SQLite через `node:sqlite` хранит JSON-записи в таблице `records(kind,id,data)` с составным ключом, транзакциями `BEGIN IMMEDIATE` и WAL. В схеме v3 крупные повторяющиеся массивы exe/правил вынесены в неизменяемые BLOB-снимки; JSON содержит внутренние ссылки, Store возвращает полные объекты. Версии физической схемы и транзакционные миграции реализованы, production-проверки ещё нужны. Пользователи, хеши сессий, клубы, каталог, устройства, enrollment и задания сохраняются на диске. Не запускать несколько API/симуляторов поверх одной БД.

Симулятор — `Core.tick`, один tick в секунду. Начальные устройства имеют стабильные ID, клуб и boot_id, регистрируются однократно при заполнении DEMO-базы. Они используют ту же очередь и валидаторы параметров, но отдельный обработчик правил в памяти/SQLite. Windows-агент никогда не вызывается из симулятора. DEMO и PILOT используют разные БД; запуск PILOT на DEMO-базе запрещён. В пилотной базе нет симуляторов и открытых демонстрационных паролей.

Windows Worker подключается только исходящими HTTP(S)-запросами. HTTP допустим только на loopback; между машинами нужен доверенный TLS. Локальный API слушает только loopback. Для будущего пилота нужен отдельно настроенный TLS reverse proxy (не развёрнут этим заданием), с очищенными forwarded-заголовками. Express доверяет только loopback proxy. Переданные proxy HTTP-запросы к агентским endpoint отвергаются, если отсутствует признак TLS.

## Состояние веб-панели

App.vue координирует вход/сессию, снимок state, выбор клуба/ПК, вкладки и отправку заданий. DeviceWorkspace, JobResults, JobBrowser, HistoryPanel и AuditPanel отвечают за свои экраны; фильтры/страницы и API-клиент вынесены в composables.

GameCatalog хранит черновик игры, ClubManagement — клуба/вариантов и enrollment, StaffManagement — сотрудников, нового аккаунта и сброса пароля. AdminManagement задаёт прежнюю двухколоночную раскладку. Общий useAdminActions получает сервисы оболочки: API, счётчик занятости, уведомления/ошибки, refresh и выбранный клуб. Он сохраняет локальные ошибки/conflict, переводит focus и отличает ошибку записи от ошибки GET после подтверждённого сохранения. Типы административных записей находятся в web/src/admin.ts; сервер остаётся окончательным валидатором.

Две административные вкладки кешируются KeepAlive в пределах аккаунта; неактивные формы убираются из DOM. При logout/401 кеш уничтожается. Черновик и expectedVersion не зависят от polling или навигации. StaffManagement перечитывает список через onActivated при каждом входе в управление, как прежний обработчик вкладки. Watch выбранного клуба продолжает очищать enrollment и у неактивного компонента. Мутации автоматически не повторяются; текущий вид и API сохранены.

## Задания

Задание содержит `id`, `batchId`, стабильный `deviceId`, `bootId`, TTL 30 секунд, фиксированную операцию, снимок игры/exe/ревизии, вариант клуба, автора, время и DEMO-признак. Никакого текста команды или скрипта API не принимает. Клубная доступность варианта проверяется при создании, перед доставкой агенту (текущие allowedVariants) и на агенте; симулятор проверяет также текущее состояние клуба.

Переходы:

- `queued → running → succeeded | failed | unknown`;
- `queued → expired` по TTL, смене загрузки или отзыву;
- `running → unknown` при потере связи/таймауте;
- `unknown → succeeded | failed` после отдельной фактической инспекции, без повторного изменения.

Недоступный ПК сразу получает `failed/offline`, команда не ждёт его неопределённо. Уже существующая queued/running/unknown блокирует следующую операцию на устройстве (консервативно блокируются и чтения из общей очереди; свежая инспекция для unknown идёт отдельным каналом). Другие устройства продолжают работу. Одновременно выдаётся максимум одно задание на устройство. Обработка статусов синхронна внутри одного Node-процесса.

Сервер сохраняет running при рестарте, истечение делает результат unknown; без доказательств успех не выставляется. Агент сохраняет receipt **до** изменения, ответ — до отправки, подтверждение доставки — после ответа сервера. Повторный job_id не исполняется второй раз. После аварии незавершённый receipt даёт unknown и инспекцию. Нельзя обещать exactly-once: авария между записью receipt и действием неотличима от аварии после действия. Проверяется состояние, а не повторяется мутация. Просроченные ID, удалённые из ограниченного кеша receipt, повторно отклоняются TTL. После смены boot_id старые команды не выполняются, состояние инспектируется без восстановления истории.

Polling 2 секунды, heartbeat — успешный poll; недоступность после 15 секунд. HTTP timeout 10 секунд, PowerShell timeout 20 секунд. До пяти попыток связи с задержками, затем cooldown 60 секунд и новый цикл; мутации при сетевых повторах не повторяются. Перед действием Worker учитывает serverTime и монотонное время poll/записи receipt; TTL проверяется по более позднему из локального и оценённого серверного времени. Смещение свыше 60 секунд даёт clock_skew. Синхронизация часов и доверенный TLS всё ещё нужны. HTTP 401/403 завершает host с кодом 1 и сохранённым outbox; отзыв не отменяет уже начатое действие мгновенно. `inspectionVerified=false` в dry-run запрещает выдавать пустой набор за фактическую инспекцию и использовать его для reconciliation.

## Правила и откат

Продуктовый префикс `PanelTech-`; имя включает game_id и нормализованный exe. Один exe — одно собственное правило. Только `Get/New/Remove-NetQosPolicy`, явно `ActiveStore`. Владение Windows-правилами определяется точным локальным manifest (имя + exe), **не одним префиксом**. При утрате manifest существующие правила считаются чужими; агент не присваивает их автоматически.

Перед apply проверяются сторонние правила, занятые имена и общие exe с несовместимым DSCP у другой игры. Общие exe с тем же DSCP допускаются; последующее переключение на несовместимый вариант конфликтует. Политики с wildcard/общими фильтрами обрабатываются консервативно. Автомиграции старых пользовательских политик нет.

Перед изменением сохраняется предыдущий собственный набор выбранной игры. Сначала удаляются только эти собственные правила, затем создаётся ожидаемый набор. После — чтение ActiveStore, проверка имён, exe, DSCP, количества и сохранности чужих/других игровых правил. При исключении пытаемся восстановить предыдущий собственный набор и проверяем откат; отдельно сообщаются failure/unknown и возможные остаточные изменения. Это последовательность с компенсацией, **не атомарная транзакция**. Системная GPO или сторонний администратор могут менять правила параллельно: в таком случае нужна ручная диагностика. После kill/питания откат не гарантируется — инспекция, без автоматического восстановления.

Успех Windows означает только подтверждение фактического набора QoS агентом. Сервер дополнительно сверяет присланный набор с ожидаемым. Это модель доверия зарегистрированному агенту, а не независимая проверка ядра Windows/сетевого трафика. Dry-run всегда имеет код `dry_run` и не становится успешным применением.

## Доступ и история

Пароли scrypt с индивидуальной случайной солью; session token 256 бит, в БД SHA-256 токена; cookie HttpOnly/SameSite=Strict, срок 8 часов, CSRF-токен для изменений, проверка Origin, ограничение неудачных входов по IP и аккаунту (10 за 5 минут, bounded process-local windows). В TLS-пилоте `SECURE_COOKIES=1`. Роль проверяется сервером. Изменение/отключение пользователя отзывает его сессии. Оператор видит все клубы, но не администрирует каталог/пользователей/регистрацию.

Enrollment: одноразовый случайный токен, 10 минут, назначение клуба администратором. После регистрации отдельный отзываемый токен устройства, в БД только SHA-256; токены не попадают в логи. Агент видит только свою очередь и может сдавать только свои результаты. Токены и receipt на агенте должны быть доступны только службе/администратору. Устройство не может само выбрать себе другой клуб или превратиться из DEMO в реальное.

Job хранит неизменяемый снимок каталога и варианта на момент создания. Отметка «помогло» отдельна от технического результата и разрешена только для успешного apply; последнее её изменение хранит автора, дату, причину и комментарий. Рекомендация выбирается по последней отметке «помогло» для точной пары device+game. Это историческая подсказка, а не текущее правило. Текущая доступность варианта проверяется заново. Полной неизменяемой истории редактирования отметок/админ-действий пока нет.

## Официальные источники, проверенные при реализации

Microsoft Learn из среды возвращал HTTP 403; содержимое прочитано через Git из официального `MicrosoftDocs/windows-powershell-docs`, ветка main:

- [New-NetQosPolicy](https://github.com/MicrosoftDocs/windows-powershell-docs/blob/main/docset/winserver2025-ps/NetQos/New-NetQosPolicy.md): AppPathNameMatchCondition, DSCPAction, ActiveStore; ActiveStore не сохраняется после reboot.
- [Get-NetQosPolicy](https://github.com/MicrosoftDocs/windows-powershell-docs/blob/main/docset/winserver2025-ps/NetQos/Get-NetQosPolicy.md): эффективный ActiveStore, поля AppPathName / DSCPValue.
- [Remove-NetQosPolicy](https://github.com/MicrosoftDocs/windows-powershell-docs/blob/main/docset/winserver2025-ps/NetQos/Remove-NetQosPolicy.md): без имени удаляет все политики хранилища; наш код всегда указывает конкретное собственное имя и ActiveStore.
- [Node SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html), [Vite](https://vite.dev/guide/), [Windows Services .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/windows-service).

Последние три ссылки — справочные; совместимость Node/Vite/Vue проверена установленными версиями и сборкой, .NET — фактической сборкой и запуском Linux dry-run. Работоспособность cmdlet на Windows этими источниками и Linux-тестами не доказана.

Целевая проверка входа/сессий/устройств и её границы: [docs/SECURITY-REVIEW.md](docs/SECURITY-REVIEW.md). Сессия истекает при expires <= now; повторный вход заменяет текущую cookie-сессию. Результат агента для queued-команды отклоняется до выдачи через poll. JSON parser работает после security headers; 400/413 не отражают тело запроса.

Аварийные границы Worker проверяются отдельным .NET executable с файловым имитатором, без Windows: [протокол проверок и восстановление](docs/AGENT-RECOVERY-TESTS.md). Повреждённое/утраченное локальное состояние вызывает остановку, а не сброс дедупликации. Linux SIGKILL не доказывает устойчивость Windows QoS или файловой системы к потере питания.

При unknown сверка использует исходный снимок задания, даже если текущие exe/варианты изменились. Совпадение старого набора не разрешает повторно применять удалённый вариант. До выдачи queued сервер повторно проверяет текущую доступность варианта; запрещённое задание не выдаётся агенту. Рекомендации прежней ревизии подписаны как исторические. Проверки и ограничения — [CATALOG-RECONCILIATION.md](docs/CATALOG-RECONCILIATION.md).

## Серверные страницы (23.10)

GET /api/history возвращает объект items/total/page/pageSize/pages/snapshot и метаданные авторов/групп, вместо прежнего массива. SQL-запросы и параметрическая валидация выделены в server/job-queries.ts, четыре partial expression index создаются идемпотентно при открытии SQLite. Workspace state ограничивает завершённую историю и отдельно сохраняет последние факты/успешное применение/«помогло» выбранной игры, все незавершённые операции остаются доступны. Страницы фиксируют верхнюю границу вставок, но не версии живых статусов; это не общий immutable snapshot. Клиенты useJobPage/HistoryPanel/JobBrowser отбрасывают запоздалые ответы и не повторяют мутации. Контракт, фильтры и границы — [PAGINATION.md](docs/PAGINATION.md). Версии схемы/online-backup реализованы следующим блоком (BACKUP-RESTORE.md); оптимизация очереди под нагрузкой остаётся открытой.

## Копии и миграции (23.10)

server/migrations.ts: user_version и журнал schema_migrations, legacy v0 принимается без переписывания records/rowid, v1 регистрирует records, v2 — индексы, v3 — общие сжатые снимки (значения и rowid сохраняются). Store выполняет поддерживаемые шаги одной транзакцией; будущая схема/несогласованный журнал не изменяются. CLI db:migrate сначала создаёт проверенный backup.

server/database-backup.ts использует SQLite Online Backup API через read-only соединение, отдельный закрытый staging и standalone DELETE-journal файл с манифестом/SHA-256. Restore копирует только в новый файл, проверяет hash повторно, мигрирует его и отзывает оперативные доступы/старые команды. Завершённые результаты сохраняются. Рабочая база и DB_PATH не заменяются. Детали и ограничения — [BACKUP-RESTORE.md](docs/BACKUP-RESTORE.md). Расписание/retention/шифрование/доставка и production recovery ещё не реализованы.

## Экономная SQLite v3 (23.10)

`server/snapshots.ts`: канонизация массивов, SHA-256 для дедупликации, raw DEFLATE только при уменьшении, небольшие массивы inline. Новые снимки и запись задания/устройства сохраняются одной транзакцией. Старые снимки не переписываются при изменении каталога или DSCP. Проверка структуры дополнена проверкой payload/hash/размера/ссылок. Store и JobQueries гидратируют полные массивы; API/.NET-контракт не меняется. Ограниченный кеш хранит строки, каждое чтение создаёт новые объекты; очередь всё ещё может сканировать все задания.

`server/database-storage.ts`: read-only статистика фактического размера main/WAL/SHM и свободных страниц. Уплотнение сначала создаёт проверенный backup и новую восстановленную базу; в staging удаляет только неиспользуемые снимки и выполняет VACUUM, сохраняя rowid для порядка страниц. Все ограничения restore сохраняются: отзыв доступов, queued expired/running unknown, отсутствие воспроизведения правил. Исходник и DB_PATH не заменяются. Синтетические замеры и инструкция — [ECONOMICAL-STORAGE.md](docs/ECONOMICAL-STORAGE.md). Retention/расписание копий, production-нагрузка и реальный Windows остаются открытыми.

## Отказы сохранения и протокола (24.10)

Store распознаёт первичные/extended SQLite ошибки хранения и приостанавливает операции до рестарта. API/health отвечает 503, таймер DEMO перехватывает исключение и приостанавливает обработку. Транзакции охватывают poll/heartbeat/смену boot/сверку/delivery, результаты с фактами устройства, DEMO-исполнение/reboot/reconcile, revoke и изменение сотрудника с отзывом сессий. Вложенные операции участвуют во внешней транзакции. ROLLBACK выполняется только для активной транзакции: SQLite может откатить её сам при SQLITE_FULL.

Worker завершает процесс при невозможности сохранить identity/receipts; сетевые ошибки сохраняют ограниченные повторы отправки outbox. Delivered записывается только после проверки ack id/device/boot/состояния. Исполнение не повторяется из-за потери ack. Ошибка исполнителя после dispatch, скачок локальных часов или истечение TTL во время действия приводят к unknown, требующему инспекции; dry-run остаётся неуспехом QoS. Контракт API не изменён, PowerShell/NetQos не изменялись. Проверки и восстановление — [FAILURE-RECOVERY.md](docs/FAILURE-RECOVERY.md). Физический носитель/питание и Windows этим не проверены.

## Audit и конкурентные правки (24.10)

Схема v4 добавляет audit records, индекс даты и три точных триггера против UPDATE/DELETE/REPLACE. Журнал создаёт server/audit.ts из allowlist-проекций, с автором серверной сессии/подтверждённого устройства. Credentials и текст комментария не дублируются. Append выполняется внутри транзакции изменения; ошибка аудита откатывает изменение и отзыв сеансов. Backup/restore сохраняют события, старые записи при миграции v3→v4 не переписываются. Прямой владелец файла/схемы остаётся доверенным, криптографического доказательства нет.

Редактирование требует expectedVersion, сравниваемый внутри BEGIN IMMEDIATE: game.revision, club/user.version (legacy 1), job.feedbackVersion (legacy 0). HTTP 409 не изменяет данные/сеансы/журнал, 428 не позволяет пропустить проверку. Feedback не повышает ревизию каталога. Клиент запоминает версию черновика независимо от polling и предлагает явную загрузку свежего состояния. Admin AuditPanel получает только серверные страницы/фильтры со стабильным insertion snapshot. Подробности/ограничения — [AUDIT-AND-EDITS.md](docs/AUDIT-AND-EDITS.md). Архитектура по-прежнему рассчитана на один API-процесс.

## Индексированная очередь и scoped state (24.10, v5)

server/queue-queries.ts: частичные индексы active(device,state) и due(expires), отдельные индексы club/token для устройств. Core.create/poll/expire/reboot и agent heartbeat/reconciliation/revoke не загружают всю завершённую историю. Poll обрабатывает сроки своего ПК, глобальный tick/state/history — все достигшие срока. FIFO — rowid. DEMO heartbeat меняет только lastSeen через JSON_SET одной транзакцией; в исполнение читаются только queued-кандидаты. Snapshot refs и boot/inspection не меняются heartbeat. Открытие текущей схемы выполняет полноценную проверку один раз, без пустого writer lock/двух повторных сканирований.

SQLite мог выбирать индекс всех succeeded вместо клуба: для workspace задан индекс клуба, для active/due/device lookup — соответствующий частичный индекс. Это устраняет зависимость горячих запросов от всей терминальной истории. Scoped state отдаёт устройства выбранного клуба и global club counters; запрос без clubId сохраняет старую неограниченную выдачу. UI sidebar использует counters. Версия v5 добавляет только индексы, без переписывания records/rowid/audit; перед обновлением db:migrate с backup.

Профили 52×65 устройств / 10k и 100k завершённых заданий, шесть клиентов панели + 32 клиента heartbeat прошли в Linux. ## Online backup под непрерывной нагрузкой (24.10)

createBackup удерживает read-only WAL transaction от проверки исходника до завершения incremental SQLite-copy. Согласованный снимок не перезапускается от commit другого API-соединения; writer продолжает работу. COMMIT освобождает reader до destination validation/hash/fsync; при исключении close освобождает его и staging удаляется. Долгий reader может временно увеличивать WAL. Timeout copy 30 секунд сохранён; поведение под заданной синтетической нагрузкой описано в docs/SOAK-TESTING.md. Формат БД/манифеста/restore не изменён.

## Жизненный цикл доступа агента (4.37 / 7.3)

server/device-access.ts обслуживает идемпотентную client-candidate регистрацию, запрос/атомарную смену credential hash и device-bound recovery grants в прежних enrollment records. Дополнительной физической миграции нет (SQLite v5): accessVersion, rotationRequested/recoveryPending и commandEpoch — логические поля. Existing device-token expression index используется прежним lookup. Audit атомарен с credential-change; secrets/hashes не попадают в state/audit.

agent/Access.cs сохраняет кандидата до POST и подтверждает его после потерянного ответа через /agent/access. Смена не меняет receipts/ID/boot. Явное локальное восстановление использует durable plan/карантин, не читает прежний outbox как новые задания и не создаёт ownership. Origin привязан к identity/файлу. Server commandEpoch блокирует старую delivery/result после восстановления; свежая инспекция старого unknown не объявляет успех потери manifest. Протокол и ограничения — docs/AGENT-ACCESS.md.

## Копии и наблюдение 4.38

`Operations` держит расписание в процессе API; тяжёлые backup/проверки/restore выполняет отдельный `backup-task.ts` без сетевого listener. Каталог привязан к пути источника, lock и метки исключают пересечение и удаление посторонних пакетов. Retention начинается после нового успешного изолированного восстановления и сохраняет минимум одну пригодную копию. Основная история не обрезается. Admin-only GET статуса читает авторизацию без записи даже при latch остановки; обычные API сохраняют блокировку. Физическая схема SQLite v5 не меняется. Настройки и границы — [OPERATIONS.md](docs/OPERATIONS.md).
